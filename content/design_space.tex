\chapter{Design Space of Graph Data Management Systems}
\label{chap:design_space}

In ~\autoref{chapter:background}, we discussed the different models used to represent graphs -- property graphs and how they can be used to materialize a structural graph. 
We also discussed the different types of workloads that can be executed on these graphs and the access patterns they exhibit.
Based on these access patterns, we identified requirements for a data structure that can be used to store graphs and discussed the different data structures that are used by graph data management systems.

In this chapter, we present a comprehensive overview of the design space of graph data management systems.
We provide a taxonomy to understand the design space of graph data management systems and discuss how different systems fit into this taxonomy.


\section{Property Graphs vs. Structural Graphs}
\label{design:property_vs_structural}
Real-world entities and their relationships can be modeled as a graph.
Since these entities have types and properties, the graph model is augmented to include these types and properties (thereby forming a schema).
We examined the formal definitions of these graph models in ~\autoref{back:graph_models}.

A structural graph can be derived from a property graph through selections and projections on the labels and properties of the graph elements.
One could select all edges of a certain type to form a structural graph, for instance, a structural graph of follower relationships in a social network.
The structural graph so constructed  “is homogeneous, composed simply of vertices, edges and, possibly, a weight attached to their elements”~\cite{teseo2021deLeo}.
The structural graph is a useful abstraction for many graph algorithms and queries, as it provides a simple graph model that can be used to reason about the structure of the graph.
For instance, the structural graph can be used to compute the connectivity of the graph or to compute the influence of a node in the graph.

We assume that the property graph is the ground truth and the structural graph is derived from the property graph.
A structural graph can be materialized as needed or periodically for analysis, as is done at Facebook~\cite{curtiss2013unicorn}.
These materialized structural graphs are essentially snapshots of the property graph at a certain point in time.
As such, these structural graphs are static and do not change over time.
We refer to these as static structural graphs and describe them in more detail in~\autoref{design:static_structural}.

In contrast, the property graph is dynamic and changes over time.
Since the property graph is the ground truth, it is important to keep the structural graph up-to-date with the property graph.
This can be done by recomputing the structural graph periodically or incrementally updating the structural graph as the property graph changes.
This leads to the concept of dynamic structural graphs, which are updated as the property graph changes.
We describe dynamic structural graphs in more detail in~\autoref{design:dynamic_structural}.

This is the primary classification feature of the design space of graph data management systems -- whether the system manages property graphs or structural graphs.
The second classification feature is whether the system is designed to handle static structural graphs or dynamic structural graphs.
We discuss these classification features in more detail in the following sections.

\section{Static Graph Processing Systems}
\label{design:static_structural}

Static structural graphs have been the main focus of graph processing systems research for over a decade.
These graphs are primarily used for analytics and graph mining tasks where the focus is on uncovering statistical properties and discovering patterns.
The static nature of these graphs implies that there is no consistency requirement between different snapshots these systems are designed to process.
Each snapshot is produced through a batch ETL process and is (often) processed independently of other snapshots.
% The primary goal of these systems is to provide a scalable and efficient way to process these graphs and to provide a rich set of graph algorithms that can be executed on these graphs.

Once the static GPS has a snapshot to process, it must first \emph{preprocess} the graph to construct the data structures needed to execute the graph algorithms.
The preprocessing step is often the most time-consuming in the graph processing pipeline.

If the graph data structures obtained after the preprocessing are small enough, they can be stored and processed in memory.
These systems are designed for shared-memory multi-core machines and are optimized for in-memory processing.
Several systems have been constructed with this design point in mind, such as Gemini~\cite{zhu2016gemini}, GraphMat~\cite{graphmat}, Ligra~\cite{shun2013ligra}, Galois~\cite{pingali2011tao}, GPOP~\cite{lakhotia2020gpop}, GraphLab~\cite{low2012distributed}, etc.

In case, the graph structures are too large to fit in memory on a single machine, the graph is partitioned across multiple machines.
These two design choices lead to two different classes of graph processing systems -- in-memory graph processing systems and distributed graph processing systems.
This is the third classification feature of the design space of graph data management systems: whether the system stores the graph in memory or on disk.
Examples of distributed graph processing systems include GraphX~\cite{gonzalez2014graphx}, Pregel~\cite{malewicz2010pregel}, PowerGraph~\cite{gonzalez2012powergraph}, Distributed GraphLab~\cite{low2012distributed}, PowerLyra~\cite{powerlyra2019}, etc.
For the purpose of creating a taxonomy, we collectively refer to shared-memory multi-core systems and distributed systems as \textbf{in-memory graph} processing systems.


Over time researchers noticed that the communication overheads in distributed graph processing systems were high leading them to underperform when compared to single-threaded systems running on a commodity laptop~\cite{mcsherry2015scalability}.
The need for building systems that can scale to large graphs that do not fit in RAM on a single machine, but the underperformance of distributed graph processing systems led to the development of out-of-core systems that store graphs on storage devices and stream them into memory as needed.
We call these systems \textbf{out-of-core graph} processing systems.
Out-of-core graph processing systems are built around the idea of caching the most frequently accessed data structures in memory and spilling the rest to disk.
The on-disk data layout is such that maximizes the sequential access to the edge data to minimize the I/O overheads.
Most systems achieve this by some form of data edge-list partitioning such that the neighbors (either in- or out-neighbors) of a vertex are stored contiguously on disk.
Examples of out-of-core graph processing systems include GraphChi~\cite{kyrola2012graphchi}, X-Stream~\cite{roy2013x}, GridGraph~\cite{zhu2015gridgraph}, V-part~\cite{elyasi2019large}, Wonderland~\cite{zhang2018wonderland}, CLIP~\cite{ai2018clip}, FlashGraph~\cite{zheng2015flashgraph}, Blaze~\cite{kim2022blaze}, etc.

The static structural graph processing systems can be seen in the bottom left corner of the design space in~\autoref{fig:design_space}.

\subsection{Programming Models vs Computation Models}
\label{design:programming_vs_computation}
The design space of static graph processing systems can be further subdivided based on the programming model and the computation models these systems are designed around.
Several survey papers~\cite{mccune2015tlavSurvey, Heidari:2018:SGP:3212709.3199523} have discussed this classification in far more detail; we present a brief overview here for completeness.

Graph processing systems are designed to execute the iterative algorithms in distinct phases.
A \textbf{Computation Models} defines these phases and the sequence in which they must be run by a graph processing system to compute the result.
The user typically writes the algorithm in terms of these phases, and the system executes the algorithm by running these phases in sequence.
The computing model is independent of the scheduling model used by the system, which determines which vertices are selected for computation (remain active) in each phase.

The most basic computation model is the \textbf{Bulk Synchronous Parallel (BSP)} model~\cite{valiant1990bridging}.
This model is based on the idea of supersteps, where the computation is divided into a sequence of supersteps, each of which consists of a computation phase and a communication phase.
The computation phase is where the user-defined function is executed on the vertices of the graph, and the communication phase is where the vertices exchange messages.
BSP model \textit{{pushes}} the updates to the vertices at the end of each superstep, and the updates are applied to the graph at the beginning of the next superstep.
Examples of systems that use this model include Pregel~\cite{malewicz2010pregel} and Giraph~\cite{giraph}.

The \textbf{Asynchronous} model is another computation model where the computation is not divided into supersteps. 
Since there is no communication barrier in this model, updates are immediately visible for the next iteration.
These systems need a consistency model for applying updates to the edges and vertices.
Examples of these systems include GRACE, ASPIRE, Giraph Unchained, CoRAL, and GraphChi~\cite{kyrola2012graphchi}.

\textbf{Gather-Apply-Scatter} (GAS) is a more general computation model that can be used to describe both BSP and Asynchronous models.
The GAS model consists of three phases: Gathering updates by \emph{pulling} them from neighbors, computing and applying the updates, and \emph{pushing} the updates to the neighbors.
Systems built using this model include GraphLab~\cite{low2012distributed}, PowerGraph~\cite{gonzalez2012powergraph}, GraphX~\cite{gonzalez2014graphx}.


Another axis to consider is the \textbf{Programming Model} used by the system.
The programming model defines the interface provided to the user to write graph algorithms and therefore defines the unit of computation in a system.
The most common programming model is the \textbf{Vertex-Centric} model, where the user writes a function that is executed on each vertex of the graph.
Each vertex program can read the state of the vertex and its neighbors and update the state of the vertex.
The user provides a \texttt{compute()} function, a \texttt{get\_value()} function to read the neighbors' state, and a \texttt{update\_state()} function to update the state of the vertex.

The \textbf{Edge-Centric} model is another programming model where the user writes a function that is executed on each edge of the graph.
Edge-centric models propagate changes by updating the state of the edge and the state of the vertices connected by the edge.
The user provides an \texttt{edge\_scatter(e)} function that sends an update over the edge $e$, an \texttt{edge\_gather(e)} function that reads the update from the edge $e$, and an \texttt{edge\_gather(e)} function that applies the update to the edge's destination vertex $e.dest$.

Another programming model is the \textbf{Partition Centric} model, where the user writes a function that is executed on each partition of the graph.
This model is used by systems that are expressly designed to reduce the cross-partition communication overhead in a distributed graph processing system.

The programming model and the computation model are orthogonal to each other, and a system can use any combination of these models.
The design space of static graph processing systems can be split based on these two axes, as shown in~\autoref{fig:static_ec_vc}.

As can be seen in the figure, the Vertex-Centric model is the most common programming model used by graph processing systems.
There are some combinations of programming and computation models that are not used by any system. 
The more interesting thing to note here is that if the system provides a flexible API to interact with the graph, the user can implement any programming model on top of the system.
\project{} is designed to provide a flexible API that allows users to implement any programming model on top of it.

\section{Dynamic Graph Processing Systems}
\label{design:dynamic_structural}
Structural graphs are derived from property graphs, and since the property graph is dynamic, the structural graph must be updated as the property graph changes.
This leads to the concept of dynamic structural graphs, which are updated as the property graph changes.
The dynamic nature of these evolving structural graphs implies that there is a consistency requirement to consider when designing these systems.
The structural graph must be updated in a manner consistent with the updates being applied to the property graph, while also making sure that any ongoing queries or computations on the structural graph are not affected by the updates.

At its most basic, a dynamic system can apply updates to the structural graph directly, without any consideration for ongoing queries.
When such a system applies an update (adding a new edge, for instance), it applies the update to the live graph data structure without creating any new versions.
Any ongoing queries that are running on the graph data structure will see the update immediately, and this leads to incorrect results, query failures, or delayed convergence of iterative algorithms.
STINGER~\cite{stinger2012ediger} is an example of such a system that allows for fast updates to the graph data structure but does not provide any consistency guarantees.

A more sophisticated approach is to construct a new version of the structural graph as the updates arrive.
Each update to the graph has a timestamp associated with it, and a system uses these timestamps to construct a versioned graph.
The system can then provide a consistent view of the graph at a certain point in time by selecting the appropriate versions of the graph elements.
Examples of systems that use this approach include GraphOne~\cite{graphone2019kumar}, LLAMA~\cite{llama}, and ASPEN~\cite{10.1145/3314221.3314598}. 

Another approach is to batch the updates and apply them together to maintain a single incremental view of the graph.
The interesting challenge in these systems is to make sure that any in-progress computations are not affected by the updates, and can continue to make progress with the new data.
These systems are designed to use incremental algorithms that can minimize redundant computations by reusing results that have been computed before the graph structure mutates.
GraphBolt~\cite{mariappan2019graphbolt}, for instance, uses "dependency-driven incremental processing, where it first tracks dependencies to capture how intermediate values get computed, and then uses this information to incrementally propagate the impact of change across intermediate values".
Kickstarter~\cite{vora2017kickstarter}, GraphIn~\cite{sengupta2016graphin}, and Tornado~\cite{shi2016tornado} are other systems that use a similar approach.

The most sophisticated approach to handling dynamic graphs is to provide a transactional interface to the user.
Transactions help a system provide some or all of the ACID guarantees to the user when updating the graph.
Good examples of transactional dynamic graph processing systems include LiveGraph~\cite{zhu2019livegraph}, Sortledton~\cite{sortledton2022Fuchs}, and Teseo~\cite{teseo2021deLeo}.
LiveGraph stores the graph out-of-core by using a mmap-based storage engine and provides a transactional interface to the user.
Sortledton is an in-memory system that provides a fully transactional adjacency-list based graph data structure.
Teseo is also in-memory and transactional, but uses a "fat tree" (B+ tree derived) data structure to store the graph.

\section{Unification of Static and Dynamic Graph Processing Systems}
\label{design:unification}
In the previous sections, we have seen that the design space of graph data management systems can be split based on whether the system manages property graphs or structural graphs and whether the system is designed to handle static structural graphs or dynamic structural graphs.
We have also seen that the design space can be split based on the programming model and the computation model used by the system.
In this section, we discuss how these two axes can be unified to provide a comprehensive view of the design space of graph data management systems.

Most in-memory graph processing systems (both static and dynamic) are designed around the data structures that we discussed in~\autoref{back:graph_rep}.
These data structures are optimized for graph analytics tasks that need sequential access to the vertex sets and the edges in a vertex's adjacency list.
These desirable properties of CSRs and Adjacency Lists make them the most common data structures used by graph processing systems, both static and dynamic.

\section{Distillation of the Design Space}
\label{design:distillation}

In the previous sections, we discussed how the design space of graph data management systems can be split based on whether the system manages property graphs or structural graphs and whether the system is designed to handle static structural graphs or dynamic structural graphs.
We also discussed how the design space can be unified based on the data structures used by the systems to store the graphs.

In this section, we provide a distilled view of the design space of graph data management systems based on the classification features we discussed in the previous sections.
So far we have identified that the design space of graph data management systems can be split based on the following classification features:
\begin{enumerate}
  \item Whether the system manages property graphs or structural graphs.
  \item Whether the system handles updates to the graph (dynamic) or not (static)
  \item Whether the system supports transactions for updating the graph
\end{enumerate}

Based on these features, we can arrive at a grid that distills the design space of graph data management systems, as shown in~\autoref{fig:distilled_design_space}.
The grid shows the different classes of graph data management systems based on these features.
As can be seen in the grid, not all combinations of these features make sense to use together, for instance, a system that only works on read-only graphs has no reason to support transactions (since there are no updates to the graph).
