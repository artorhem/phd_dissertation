\chapter{\project{} Architecture}
\label{chapter:architecture}

The previous chapters have described what graphs are, the graph models commonly used to represent real-world entities (property graphs), and how those can be refined to extract purely structural graphs for analyzing some particular relationships and perform statistical analysis on them. 
We also discussed different graph workloads that are commonly used on graph data, and which data structures are most commonly used to support these workloads.
In this chapter, we will describe the architecture of \project{}, a graph database that is designed to support the workloads described in Section~\autoref{back:workloads}.

If graph processing systems are specialized for analyzing the structure of the graph, then graph databases are the general-purpose systems that are designed to \emph{store and manage} property graphs -- the most general model of entity and relationship mappings.
Consequently, a graph database architecture must be such that it allows efficient storage and retrieval of graph structure and properties while being able to support the broad range of graph workloads that we discussed in~\autoref{back:workloads}.

However, as we discussed, the graph structure is a projection of the property graph and can be derived from it. 
Additionally, the graph structure is used for analytics tasks which are more computationally intensive than the point queries and neighborhood queries that are common on property graphs.
Therefore, it is logical for a graph database to handle the graph structure independently of the properties and the labels associated with the nodes and edges.
The layout optimizations needed by the structure of the graph can be different from those needed by the properties and labels, and this separation allows for more optimization opportunities.

\project{} made this architectural decision to separate the graph structure from the properties and labels pretty early on in the design process.
So far, the development of \project{} has been focused on the graph structure, and we have only prototyped the ability to store properties.
Although \project{} does not handle properties, we have spent considerable time in designing the system such that adding the properties does not require duplicating the structure nor does it affect the performance of the analytics workloads we will show in this chapter and ~\autoref{chapter:evaluation}.


The chapter breakdown of this thesis mirrors our decision to store the structure and properties of the graph independently.
This chapter focuses on the structure of the graph, detailing our architecture for managing structural graphs.
We build upon this architecture in ~\autoref{chapter:propertyGraphs}, where we discuss our approach to storing properties.
There are two proposals for storing property and label information – inline with the element or separately using column stores
We provide mechanisms to do both and perform a comparative study of how they perform under a variety of workloads

\emph{For the rest of this chapter, we will use the term graph to refer to a structural graph unless explicitly mentioned otherwise, and we use the term graph database to describe \project{} even though it does not yet handle property graphs.}

The remainder of this chapter is organized as follows: we begin with a description of a common application to understand how the graph database is designed to make this application run efficiently.
We then describe the architecture of \project{} and the three components that make up the system.
Following that, we describe how this architecture is implemented in the current prototype of \project{}, covering our storage engine, the design of our API to interact with the graph, the graph representations we support, and the higher-level traversal primitives we support.
We close with a description of our methodology for managing temporary graph properties and our design of an efficient bulk loader.

\section{What should a Graph Database Provide?}
In section~\autoref{back:workloads}, we discussed the different workloads that are commonly used on graph data and the access patterns they exhibit.
We also discussed the data structures that are commonly used to support these workloads.
A graph database, therefore should provide the following features:
\begin{itemize}
\item A GDB must store the graph in \textbf{formats} that facilitate high-performance analytics by supporting the workload’s access patterns 
\item A GDB must provide a high-level \textbf{API} that abstracts the underlying data structures and provides a simple interface for the user to interact with the graph. The user does not need to know the internal representation of the graph to use and query her data.
\item A GDB must provide a \textbf{framework} to support fast graph operations and traversals. Efficient iterators on the graph elements are critical for performance and should be first-class primitives in the system.
\end{itemize}

To implement the PageRank algorithm in a graph database requires accessing the following distinct parts of the graph:
\begin{itemize}
\item We need to access the vertex set to initialize the scores and the outgoing values.
\item For each node, we need to access the incoming neighbors to compute the incoming total and update scores
\item We need to access the scores of each node to update the outgoing values
\end{itemize}
