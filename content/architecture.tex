\section{Design Principles}
\label{arch:design-principles}

% Two key ideas:
% 1. Separation of structure and properties — topology in B-tree keys,
%    properties in separate tables. Contrast with TuGraph (co-located blobs)
%    and GraphflowDB (in-memory CSR).
% 2. KV store as persistence layer — why WiredTiger (MVCC, non-blocking reads,
%    larger-than-memory). Brief treatment, not a full subsection.
% 3. Transaction semantics: snapshot isolation, single-process multi-threaded
%    model, sessions and cursors. One paragraph, not its own subsection.

A graph database architecture must allow efficient storage and retrieval of both structural and property graphs while supporting the breadth of workloads that we discussed in~\autoref{sec:bg:workloads}.
Since \mbox{analytics} tasks operate on the structural graph while point and neighborhood queries access properties, a graph database must handle both efficiently.
Therefore, we conclude that a \textbf{graph database should store the graph structure independent of the properties and the labels associated with the nodes and edges.}
% The layout optimizations needed by the structural graph can be different from those needed by the properties and labels, and this separation allows for more optimization opportunities.

We use the \wt{} key-value store as our persistence layer, because it provides %key benefits that are crucial for performance: 
excellent multi-threaded (non-blocking) read performance, ACID-compliant MVCC reads, and the ability to scale to datasets larger than RAM.
These properties are essential for efficient read-heavy analytics tasks that are common in graph processing workloads. 

Since \wt{} is an embedded KV store, \project{} runs as a single process: each thread opens a private session with its own cursors, so reads never contend across threads.
Writes use snapshot isolation; concurrent writes to the same key are resolved by committing one transaction and rolling back the rest.

\section{Structural Representations}
\label{arch:structural-reps}

% We saw in~\autoref{sec:bg:reps} that most structural graph processing systems use a CSR-like or Adjacency List-like representation to store the graph.
% A graph database should be able to persist these data structures to disk in a way that allows for efficient reconstruction and access.
% The database designer must identify how to store them in the storage engine and do so in a way that preserves the locality of access to vertices and their neighborhoods.

% For storing a CSR, the database must store all incoming/outgoing edges for each vertex in a contiguous "chunk" and provide an index (or search) to identify the start and end of the chunk.
% To store an adjacency list, the neighborhood of each node must be materialized and stored in-line with the node; the nodes must be laid out sequentially in some ordering of their IDs.

\project{} provides two graph representations that mimic the two most common layouts used in in-memory graph processing: Adjacency Lists (\autoref{arch:adjlist}), and EdgeKey (\autoref{arch:edgekey}), which approximates a CSR.
In \project{}, vertex IDs are 64-bit unsigned integers, degree counts are 32-bit unsigned integers, and edge weights are double-precision floats per the Graphalytics~\cite{capotua2015graphalytics} specification.

Both representations store vertex and edge IDs as big-endian 8-byte blobs so that \wt{}'s lexicographic key comparison (\texttt{memcmp}) coincides with numeric order; we explain this encoding and its advantages in \autoref{arch:typed-ids}.

\subsection{Adjacency List Representation}
\label{arch:adjlist}
% Tables: adjlistout, adjlistin (directed), optional node table (read-optimized).
% Value format: [degree | neighbor_ids...] as a raw byte blob.
% WT_MODIFY for O(1) delta-append without rewriting the full neighbor list.
% This is why adjlist tables are "frozen" (value_format=u, no typed columns) —
% a real design tension with property storage.
The adjacency list representation uses two adjacency tables to store in- and out-neighborhoods separately (\autoref{fig:schema:adjlist}).
Each adjacency table is keyed by a big-endian vertex ID; the value is a packed byte blob containing the vertex's degree followed by its neighbor IDs.
This format allows us to modify adjacency lists via the \code{WT\_MODIFY} API, which stores a change record (an offset, a length, and replacement bytes) in the \wt{} cache and write-ahead log (if enabled) instead of rewriting the entire adjacency list value.
This format has implications for property storage discussed in \autoref{arch:prop-embedded}.
For undirected graphs, a single adjacency table stores each edge $(a\text{ --- }b)$ as two directed entries: $(a \rightarrow b)$ and $(b \rightarrow a)$. 

In read-optimized mode, an additional node table stores each vertex's in-degree and out-degree, avoiding a full adjacency-list scan for degree queries. 
For weighted graphs, a separate edge table with composite key $(src, dst)$ stores edge weights.

\subsection{EdgeKey Representation}
\label{arch:edgekey}
% Sentinel design: nodes and edges interleaved in one sorted B-tree.
% OOB sentinel (dst=0) for node entries; MAKE_EKEY(id) = id+1 shift.
% Separate edge_out and edge_in tables (directed); single edge_out (undirected).
% Topology in keys, not values — traversal touches zero value bytes.
The EdgeKey representation stores vertices and edges in a single sorted B-tree, keyed by ($src\_id, dst\_id$).
A reserved out-of-band destination ID (\texttt{0}) marks vertex entries; all other entries are edges.
The value is interpreted as follows:
\begin{itemize}
  \item For node entries, the value contains the serialized \code{in\_degree} and \code{out\_degree} in read-optimized mode or a 1-byte dummy value in the (default) write-optimized mode.
  \item For edge entries, the value contains the edge weight for weighted graphs or a 1-byte sentinel (\texttt{0x00}) for unweighted graphs.
\end{itemize}
Lexicographic key order guarantees that each node entry precedes its outgoing edges.
To scan the out-neighborhood of \code{src\_id}, we position the cursor at \code{(src\_id, 0)} and iterate over all keys with prefix \code{src\_id}.

% Since \texttt{0} is reserved for node sentinels, all user-provided IDs are transparently shifted by +1 before storage to avoid collisions.
% Since \texttt{0} is reserved for the node sentinel, every ID is unconditionally shifted by $+1$ during insertion and shifted back by $-1$ during retrieval.
For directed graphs, two edge tables, $edge\_out$ and $edge\_in$, avoid a secondary index for in-neighborhood access; $edge\_in$ is keyed on $(dst\_id, src\_id)$ and is not exposed through the API.

\input{content/fig/schema_edgekey}
The EdgeKey representation encodes topology entirely in keys: a structural traversal iterates over keys without calling \code{get\_value()}.
With 1-byte sentinel values for unweighted edges, leaf pages achieve high key density, reducing the number of pages touched per neighborhood scan.

\subsection{Comparison}
The two representations offer complementary tradeoffs.
The adjacency list stores each vertex's full neighborhood in a single blob, enabling fast sequential reads in one I/O, but edge insertions require a read-modify-write cycle (mitigated by \code{WT\_MODIFY} delta records), and concurrent insertions to the same vertex contend on the shared blob.
EdgeKey encodes topology in keys, avoiding value deserialization during traversal, and each edge insertion is an independent key-value pair with no contention on existing rows.
The cost is that reading a full neighborhood requires scanning multiple B-tree entries rather than deserializing a single blob.

\section{Property Storage}
\label{arch:property-storage}
Labels assign vertices a type, and we use the terms interchangeably.
Thus, vertices with the same label share an attribute schema (\autoref{sec:bg:model}), and vertices with different labels can have different schemas, e.g., a \texttt{Person} vertex has \texttt{age} and \texttt{email} columns, while a \texttt{Post} vertex needs only a timestamp and a poster ID.
The database must therefore (1)~identify each vertex's label so it can apply the correct schema, and (2)~store the attributes in a layout that supports both point lookups and analytical scans.
\project{} addresses these two concerns with \emph{labeled vertex IDs} and two \emph{property storage modes}: embedded and columnar.
% We treat each label as a distinct type, and use these terms interchangeably.
\subsection{Labeled Vertex IDs}
\label{arch:typed-ids}

When a graph contains vertices of different labels, we want to infer a vertex's type from its ID to avoid a table lookup to determine a vertex's schema.
\project{} reserves the top 8 bits of the 64-bit vertex ID as a \emph{label tag}; the remaining 56 bits hold a label-local vertex ID:
\[
  \texttt{id} = \underbrace{L}_{\text{8 bits}} \;\|\; \underbrace{\text{counter}}_{\text{56 bits}}
\]
Extracting the label is a single shift, and the range of all vertices with label~$L$ is a static interval; neither requires runtime state:
\[
  \textsc{vtype\_of}(\texttt{id}) = \texttt{id} \gg 56
  \qquad
  \text{range}(L) = \bigl[L \ll 56,\; (L{+}1) \ll 56\bigr)
\]

Because \wt{} sorts keys lexicographically via \texttt{memcmp}, all IDs are stored as big-endian 8-byte blobs: big-endian layout makes byte order coincide with numeric order, and raw comparison avoids the decoding overhead of \wt{}'s native variable-length integer formats (\texttt{I}, \texttt{Q}).
After this byte-swap, the label tag occupies the first byte of the stored key, so \wt{}'s lexicographic comparison groups vertices with the same label contiguously in the B-tree.
A label-filtered scan is therefore a simple key-range bound.

Edge labels are determined implicitly from the labels of their endpoints.
We assume that each pair of endpoint labels maps to exactly one edge label, a condition that holds in the LDBC Social Network Benchmark~\cite{capotua2015graphalytics} schema.
Under this assumption, no label column is needed in the edge key, and the edge label is recovered by inspecting \code{VTYPE\_OF(src)} and \code{VTYPE\_OF(dst)}.

This design contrasts with two alternatives.
TuGraph~\cite{linBuildingHighPerformanceGraph2024} stores the label in the vertex \emph{value}, requiring a value read to determine it.
GraphflowDB~\cite{graphflowdb2021Gupta} assigns consecutive ID ranges per label, but the range boundaries depend on the actual vertex counts at load time.
\project{}'s bit-reservation gives $O(1)$ label extraction with boundaries that are fixed at schema definition time.

\subsection{Embedded Mode}
\label{arch:prop-embedded}

In embedded mode, properties are stored as an opaque byte blob alongside the structural data.
For the EdgeKey representation, vertex properties are appended after the degree bytes in the vertex entry: the value of a vertex entry becomes \texttt{[in\_degree\,|\,out\_degree\,|\,property\_blob]}.
Edge properties are stored in the edge row's value field.
Reading a vertex's properties and degree thus requires a single cursor lookup.

AdjList cannot embed properties, because the \code{value\_format=u} required by \code{WT\_MODIFY} (\autoref{arch:adjlist}) precludes "typed" columns; it instead uses a scheme similar to that of TuGraph, storing properties in separate \code{node\_props} and \code{edge\_props} tables, keyed by the same IDs, with the schema determined by \code{VTYPE\_OF(id)}.

The embedded layout incurs a write-amplification cost in the EdgeKey representation: every edge insertion that updates a vertex's degree must rewrite the full sentinel row, including the appended property blob.
For a vertex label with a 145-byte attribute schema, each degree update rewrites at least 153 bytes, even though only 8 bytes (the degree pair) changed.

\subsection{Columnar Mode}
\label{arch:prop-columnar}

In columnar mode, properties are stored in separate \emph{per-label} tables with \wt{} column groups.
Each vertex label gets its own property table (e.g., \code{person\_props}, \code{post\_props}), and each edge label with properties gets a dedicated table (e.g., \code{knows\_props}, \code{likes\_props}).

\wt{} column groups physically split tables' value columns into separate B-trees; a cursor opened on one column group reads only that group's pages.
For instance, in the LDBC SNB schema, a Person vertex's properties can be organized into three column groups:
\begin{itemize}
  \item \code{temporal}: \texttt{creationDate}, \texttt{birthday} (16\,B/row, fixed-size)
  \item \code{name}: \texttt{firstName}, \texttt{lastName}, \texttt{gender} (variable-size)
  \item \code{contact}: \texttt{browserUsed}, \texttt{locationIP} (variable-size)
\end{itemize}
An analytical query that filters vertices by creation date scans only the \code{temporal} B-tree, reading 16 bytes per row instead of the full property record.

The central principle is to \textbf{separate fixed-size, scan-friendly columns from variable-length ones}: fixed-size groups yield high row density per page, while isolating variable-length columns keeps large blobs out of the cache during narrow scans.

Both representations use the same per-label property tables in columnar mode: for AdjList, this replaces untyped blob tables with typed column-group tables; for EdgeKey, the sentinel row shrinks to 8 bytes (degrees only), keeping the structural B-tree compact.
\autoref{fig:schema:property} contrasts the two modes.

To our knowledge, \project{}is the first system to provide \textbf{disk-based columnar property access on a graph storage engine}; per-column I/O isolation inherits \wt{}'s ACID transactions, MVCC, crash recovery, and buffer pool management without re-implementation.
GraphflowDB~\cite{graphflowdb2021Gupta} achieves columnar access but operates entirely in memory; TuGraph~\cite{linBuildingHighPerformanceGraph2024} is disk-based but packs all properties into a single blob with no per-column isolation.

Multi-valued attributes (e.g., a set of email addresses) cannot be stored in typed columns.
These are handled by secondary tables with composite keys \texttt{(vertex\_id, index)}, storing one value per row, retrieved via a prefix range scan on the vertex's ID.

\section{Graph API and Cursor Architecture}
\label{arch:api}

\project{} exposes a C++ library API with two layers: \code{GraphEngine} owns the \wt{} connection, manages checkpoints, and handles partitioning; it creates \code{GraphBase} handles for graph operations.
\code{GraphBase} is an abstract class with virtual methods for node/edge manipulation and property access; \code{AdjList} and \code{SplitEdgeKey} each provide a concrete implementation, so application code is unaware of the underlying storage layout.

\textbf{Topology cursors} provide bulk operations such as scanning all nodes or iterating a neighborhood.
\project{} defines four abstract cursor classes: \code{OutCursor} (out-neighborhood), \code{InCursor} (in-neighborhood), \code{NodeCursor} (node iteration), and \code{EdgeCursor} (edge iteration).
Each representation provides its own cursor implementation: for example, \code{AdjOutCursor} deserializes the packed neighbor blob from a single adjacency table entry, while \code{SplitEKeyOutCursor} iterates successive keys in the edge B-tree.

\textbf{Property cursors.}
Analytical queries often scan a single attribute across many vertices.
\code{Node\-Prop} cursor and \code{Edge-Prop} cursor exploit the column-group layout (\autoref{arch:prop-columnar}) to read individual columns via typed accessors (e.g., \code{get\_uint64(n)}).
In columnar mode the cursor reads only that group's B-tree pages; in embedded mode it extracts the field from the property blob.
\code{GraphBase} factory methods select the implementation, so query code is mode agnostic.

\subsection{Partitioning for Parallel Analytics}
\label{arch:api:partitioning}

For running multi-threaded analytics, \texttt{GraphEngine} pins a read-only checkpoint and divides the vertex set into disjoint key ranges.
Each thread receives its assigned range and creates its own topology and property cursors scoped to that range.
\project{} provides three partitioning strategies.
\code{NODE\_COUNT} divides the vertex set into equal-sized partitions by node count.
\code{EDGE\_AWARE} (default) partitions by accumulated out-degree so that each partition contains roughly the same number of edges, balancing work for degree-skewed graphs.
\code{NODE\_COUNT\_FINE} is a finer-grained variant that creates \texttt{num\_threads} $\times$ \texttt{partition\_scale} partitions for work-stealing schedulers.
For even finer granularity, \code{get\_work\_chunks(chunk\_size)} returns a vector of small, fixed-size key ranges suitable for task-queue-based parallelism.
