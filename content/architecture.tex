\chapter{\project{} Architecture}
\label{chapter:architecture}

We now introduce the \project{} Graph Database architecture. Our goal in designing \project{} is to achieve the performance of purpose-built graph-processing systems in the context of a transactional, dynamic, property-graph system.
We developed \project{} through iterative refinement, first investigating ways to get a production storage engine to mimic state-of-the-art in-memory structures.
Next, we developed a programmatic API capable of implementing all the programming models cataloged in Section~\autoref{design:programming_vs_computation}.
Finally, we continued to refine the design to support the range of workloads described in Section~\autoref{back:workloads}.

If graph processing systems are those systems specialized for analyzing graph structure, then graph databases are the general-purpose systems designed to \emph{store and manage} property graphs.
Consequently, a graph database architecture must allow efficient storage and retrieval of both graph structural and properties while being able to support the broad range of graph workloads that we discussed in~\autoref{back:workloads}.
Importantly, as computationally intensive analytics tasks operate on the structural graph, not the property graph, the challenge for graph databases is providing efficient analytic processing in the presence of the easier point queries and neighborhood queries that are common on property graphs.
Therefore, we conclude that a graph database should store the graph structure independently from the properties and the labels associated with the nodes and edges.
The layout optimizations needed by the structural graph can be different from those needed by the properties and labels, and this separation allows for more optimization opportunities.

\project{} embraces this architectural decision to separate the graph structure from the properties and labels.
Since providing good performance on analytics tasks is the more challenging the problems we address, development to date has focused primarily on this problem. While we have prototyped the rest of the property graph implementation, further design and implementation remains part of future work, which will be described in ~\autoref{chapter:propertyGraphs}.

Although \project{} does not yet handle properties, we have spent considerable time designing the system such that adding properties does not require duplicating the structure nor does it affect the performance of the analytics workloads we evaluate in ~\autoref{chapter:evaluation}.


The chapter breakdown of this thesis mirrors our decision to store the structure and properties of the graph independently.
This chapter focuses on the structure of the graph, detailing our architecture for managing structural graphs.
We build upon this architecture in ~\autoref{chapter:propertyGraphs}, where we discuss our approach to storing properties.


\emph{For the rest of this chapter, we use the term graph to refer to a structural graph unless explicitly mentioned otherwise, and we use the term graph database to describe \project{}, even though it does not yet handle property graphs.}

The remainder of this chapter is organized as follows: we begin with a description of a common application to understand how the graph database is designed to make this application run efficiently.
We then describe the \project{} architecture and the three components that make up the system.
Following that, we describe how this architecture is implemented in the current prototype, discussing our storage engine, the design of our API, the graph representations we support, and the higher-level traversal primitives we support.
We close with a description of our methodology for managing temporary graph properties and our design of an efficient bulk loader.

\section{What should a Graph Database Provide?}
In section~\autoref{back:workloads}, we discussed the different workloads that are commonly used on graph data and the access patterns they exhibit.
We also discussed the data structures that are commonly used to support these workloads.
A graph database, therefore should provide the following features:
\begin{itemize}
\item A GDB must store the graph in \textbf{formats} that facilitate high-performance analytics by supporting the workload’s access patterns 
\item A GDB must provide a high-level \textbf{API} that abstracts the underlying data structures and provides a simple interface for the user to interact with the graph. The user does not need to know the internal representation of the graph to use and query her data.
\item A GDB must provide a \textbf{framework} to support fast graph operations and traversals. Efficient iterators on the graph elements are critical for performance and should be first-class primitives in the system.
\end{itemize}

Let us examine the following running use case, computing PageRank on a graph, as motivation for this list of requirements.
The pseudocode for the PageRank algorithm is shown in Algorithm~\autoref{alg:PageRankPullGS}.

\begin{algorithm}
  \begin{algorithmic}[1]
  \Require Graph $G = (V,E)$ where $V$ is the set of nodes and $E$ is the set of edges
  \Require Damping factor $kDamp \in (0, 1)$, typically $d = 0.85$
  \Require Tolerance $\epsilon > 0$, typically $10^{-4}$
  \Ensure PageRank vector Scores
  \State Initialize $init\_score = \frac{1.0}{|V|}$
  \State Initialize $base\_score = \frac{1.0 - kDamp}{|V|}$
  \State Initialize $Scores(v) = init\_score$ for all $v \in V$
  \State Initialize $Outgoing\_vals(v) = 0$ for all $v \in V$
  \ForAll{\highlightP{$v \in V$}}
      \State \highlightM{$Outgoing\_vals(v) \gets \frac{init\_score}{|N^+(v)|}$}
  \EndFor
  \For{$i = 1$ to $max\_iters$}
      \State $\Delta = 0$
      \ForAll{\highlightP{$v \in V$}}
          \State $incoming\_total = 0$
          \ForAll{\highlightB{$u \in N^-(v)$}}
              \State $incoming\_total \gets incoming\_total + Outgoing\_vals(u)$
          \EndFor
          \State $old\_score \gets Scores(v)$
          \State \highlightM{$Scores(v) \gets base\_score + kDamp \cdot incoming\_total$}
          \State $\Delta \gets \Delta + (Scores(v) - old\_score)$
          \State \highlightM{$Outgoing\_vals(v) \gets \frac{Scores(v)}{|N^+(v)|}$}
      \EndFor
      \If{$\Delta < \epsilon$}
          \State \textbf{break}
      \EndIf
  \EndFor \\
  \Return $Scores$
  \end{algorithmic}
  \caption{PageRank Algorithm as specified in GAP Benchmark. The highlighted lines indicate different accesses: \highlightP{access to the vertex set}, \highlightB{access a vertex's neighborhood}, and \highlightM{the results vector}.}
  \label{alg:PageRankPullGS}
  \end{algorithm}
