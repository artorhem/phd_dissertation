\chapter{Background and Motivation}
\label{chapter:background}
A graph processing system can be characterized by the workload it is designed to serve, the computational model it provides, and the data layouts maintained in memory and on disk to achieve good performance.
In this section, we discuss how graphs are represented in memory (section~\autoref{back:graph_rep}) and how these representations can be efficiently stored externally when the graph does not fit in the main memory (section~\autoref{back:persistent_rep}). 
We follow this discussion by examining the computational models (section~\autoref{back:programming_model}) commonly used by graph-processing systems and how they interact with and rely on the data layouts (both in-memory and persistent).
Next, we examine graph workloads (section ~\autoref{back:workloads}) —both transactional and analytical— and then in section~\autoref{back:programming_model}, examine how the programming and computational model interact with the data layout and are influenced by with workload.
We conclude this section with a discussion of graph databases and how they are the primary candidate to bridge the archipelago of graph transactional and graph analytics systems.

\section{Graph Representations}
\label{back:graph_rep}
\TLS{A graph is defined as a pair $G = (V, E)$ of sets $V$ and $E$ such that $E \subseteq [V]^2$; $V$ is the set of \textit{vertices} of the graph $G$, and $E$ is the set of \textit{edges} of $G$\cite{diestel2017basics}.}
The vertices are the entities modeled by a graph, and an edge represents a relation between the vertices to which it connects.
The canonical representation of a graph uses an $n \times n$ matrix $A$, where $n$ is the number of vertices in the graph; an element $a_{ij} = 1$ in $A$ indicates the presence of an edge between vertices $i$ and $j$.
Depending on the matrix's definition, edges can be directional or non-directional (we use the term \textit{undirected graphs} to refer to these). 
Hence, the edge $a_{ij}$ can either indicate a directed edge $i \rightarrow j$ or an undirected edge $i \leftrightarrow j$.
It is common to represent undirected edges between vertices $i$ and $j$ as two directed edges $i \rightarrow j $ and $j \rightarrow i$.

\TLS{Real-world graphs tend to follow the power law distribution, have small diameters, and exhibit communities ~\cite[Section~2]{chakrabarti2006GraphMining}.}
A power-law distribution of degrees leads to a few \textit{hub} nodes with very high degrees and many nodes with very low degrees (heavy tail of degree distribution)\PM{insert a log-log plot of degree distribution.}
A direct consequence of the power law graph is that the resulting adjacency matrices are sparse and, therefore, memory inefficient.
~\autoref{fig:back:soc_epinions} shows the adjacency matrix and the degree distribution plots for \texttt{soc-epinions1}~\cite{soc-epinions1:SNAP}, a small network with around 76000 nodes.
The white space in the adjacency matrix visualization denotes the sparsity pattern, which translates to empty cells in a $n*n$ two-dimensional array representation of the graph.
This wasted space in an adjacency matrix leads to poor cache utilization, which is already challenging due to the random access pattern inherent in graph traversal.
Using better data structures that are more compressed than an adjacency matrix is essential to minimize the space requirement and maximize cache utilization. 

We now examine a few memory-efficient data structures commonly used in graph processing systems and the cost of creating, updating, and finding neighborhoods of a node in each representation.

\label{back:adjlist}
\TLS{Adjacency lists are a natural evolution from adjacency matrices and are constructed by breaking down the graph into per-vertex neighborhood lists.}
For instance, consider the adjacency matrix shown in ~\autoref{fig:back:sample_adj_matrix}.
To construct the neighborhood list for each node, we construct a vector containing the column index $j$ where $a_{ij} = 1 $ in the adjacency matrix.

The memory requirement for the adjacency list representation is $O(|V| + |E|)$, which is superior to the $O(V^2)$ required for an adjacency matrix.

\TLS{Adjacency lists allow sequential access to a node's neighborhood, however, a random seek is required to access the neighborhood (the vertex contains a pointer to the list).}
This is a dynamic data structure: inserting new edges into an unsorted adjacency list representation has an amortized $O(1)$ cost, however, if the list must be kept sorted, the cost increases to $O(log(n))$.
Typically, there are two adjacency lists maintained for a graph: one for the in-neighborhood and another for the out-neighborhood.

\subsection{Compressed Sparse Row}
\label{back:CSR}
\TLS{Compressed Sparse Row(CSR) ~\cite{saad2003iterative} is a very compact, \emph{immutable} data structure that uses two flat arrays to store the neighborhood lists for nodes in a graph.}

Assuming we have a non-symmetric sparse matrix A, we create two integer vectors: \emph{vertices} and \emph{edges}.
For each $v_i \in V$, \emph{vertices[$v_i$]} = $idx_{v_i}$; where $idx_{v_i}$ is the index in \emph{edges} where $v$'s adjacency list begins.
The contents of \emph{edges}[idx${v_i}$] to \emph{edges}[idx$_{v_i+1}$] are the sets of vertices $v_j$ such that $a_{ij} \neq 0$.
CSR stores a graph $G = (V,E)$in $O(|V| + |E|)$, but since it is immutable, needs reconstruction upon any changes to the graph.
Inserting new edges into CSR format takes time that is linear in the size of the graph in the worst case.

\subsection{Hybrid CSRs}
\label{back:mutableCSR}
\TLS{CSRs are efficient for storing and traversing static graphs, however, they need to be reconstructed when the graph evolves.}
The edge array might need reallocation to accommodate an incoming edge, and the old edges must be moved and shifted around the new edge.
This is a pretty serious limitation for evolving graphs, and a lot of research has been done to create resizable CSRs for graphs.

Three types of insert-friendly CSRs are commonly used:
\begin{enumerate}
    \item \textbf{In-place Updates}: These data structures are created in a way that allows for in-place insertion and deletion of graph elements without needing a full expensive rebuilding of the data structure.
    NetworKit\cite{staudt2014networkit} doubles the size of the initial array and reserves space for new edges being inserted into the graph. 
    A variant of the CSR called the Packed CSR \cite{PackedCSR} leaves space between elements which allows for faster insertion and deletion of graph elements at the cost of a slowdown in traversals and an increase in the space overhead. 
    \item \textbf{Batching updates}: Many systems batch updates and preprocess the updates to make the insertions faster.
    Systems such as the one described by Madduri et. al. \cite{madduri2009compact} batch updates, order them by vertex ids and sort them before applying the updates.
    \item \textbf{Multi-versioning and Delta Updates}: An alternative design to support fast inserts into a graph is to store all updates in a separate structure called a Delta Map.
    This use of delta maps allows for running graph analytics on snapshots of the graph at different times in its evolution.
    LLAMA\cite{llama} is one such snapshot-based graph system that supports multi-versioning and stores the delta updates as separate concurrently accessible snapshots. 
    There are some downsides to using a snapshot-based system for analytics. 
    A high ingestion rate leads to a lot of delta snapshots, which can degrade the performance of analytics tasks because updates get scattered over multiple snapshots, and these need to be read for running jobs.
    This can be remedied by merging and consolidating updates into the CSR by a process called compaction. It is similar to garbage collection and is expensive and leads to latency spikes.
\end{enumerate}

\section{Persistent Graph Layouts}
\label{back:persistent_rep}
\TLS{Graphs can be large and grow to a size that they cannot fit in RAM.}

\TLS{Common graph algorithms traverse the graph by accessing each node's neighborhoods.}
Sequential access is critical for an out-of-core system.
Even on the best SSDs, sequential access is still significantly faster than random access, so semi-external processing is critically dependent on good data layouts.
Persistent graph layouts are, therefore, designed to support the graph processing system in accessing the relevant sub-graph or neighborhood as efficiently as possible.
Most semi-external graph processing systems spend a significant amount of time preprocessing the data to construct a sequential data layout.
The layout must be designed in cooperation with constructing data traversal schemes that minimize conflicts when updating the in-memory state and maximize cache reuse.
Underpinning all this effort is an efficient storage engine that interleaves computation with IO requests, handles the file or block IO, and provides some atomicity-consistency-isolation-durability (ACID) guarantees (if the system has been designed to provide any).

\TLS{GraphChi~\cite{kyrola2012graphchi}, for example, processes a graph in \emph{parallel sliding windows} of vertices, and the data layout is such that computation threads processing a certain window can read all incoming edges to vertices in that window by reading in a single disk-based shard.}

\TLS{X-Stream~\cite{roy2013x} takes a different approach to maximize sequential access to the edge data.} 
Unlike GraphChi, X-Stream streams the edges and updates the vertex states in memory (the number of edges is an order of magnitude more than the number of nodes in many graphs), instead relying on the sheer parallelism of using RAID groups.
X-Stream uses the notion of a \emph{streaming partition}, which is a subset of vertices and all the edges with a source vertex in that subset. 
The graph is partitioned by the source vertex of the edges. The graph is processed by streaming in the edges of a streaming partition and keeping the vertex state in memory.
The premise is that partitioning a graph by the source vertex ID is less computationally expensive than sorting the edges, as GraphChi does. A strict ordering of edges within a partition is not required with X-Stream. This is why the authors claim that X-Stream does not need any preprocessing.

\section{Graph Processing Programming Models}
\label{back:programming_model}
\TLS{Since all graphs can be expressed as sparse matrices, all graph computations can be considered matrix operations. For instance, graph processing algorithms can be expressed as: }
\begin{equation}
    Y = X^{T}A
\end{equation}
where $X$ and $Y$ are vectors of vertex states, and $A$ is the sparse adjacency representation of the graph.
Semi-External graph processing essentially keeps the vertex states (or parts of the vertex state) in memory, and the data layouts are designed to maximize sequential access to $A$ that matches the order in which $X$ and/or $Y$ are accessed.

In a single-node system, the computation model defines:
(i) [IO]is A read in its entirety each time, or is there some reasonable way to access a subgraph, ideally only the neighborhood needed (all: naive linear algebra, whole matrix in a smart way: x-stream, only relevant edges: most systems)


(ii) [Consistency Semantics] Is Y immediately visible? In this scenario, the system designer has two options: distributing computation to multiple machines with enough aggregated RAM to store the graph or running the computation on a single machine caching part of the graph and any algorithmic state in main memory, with the entire graphs on persistent storage (e.g., a flash drive).

\subsection{Semi-External Graph Processing Systems}
\TLS{DRAM is an expensive resource and can account for roughly 30\% of the cost of a modern datacenter~\cite[Figure~1]{weiner2022tmo}.}
With the unrelenting growth of graph dataset sizes, keeping all the graph data in memory is increasingly untenable.
Fortunately, fast solid-state devices, such as NVMe devices have become widely available, and they present another architectural opportunity for graph processing: semi-external graph processing systems.
In this architecture, a small subset of the graph and some algorithmic state is maintained in memory (tunable based on the memory budget); the rest of the graph is streamed from slower external storage.
Popular systems that are built with this architecture include GraphChi~\cite{kyrola2012graphchi}, X-Stream~\cite{roy2013x}, GridGraph~\cite{zhu2015gridgraph}, FlashGraph~\cite{zheng2015flashgraph}, Blaze~\cite{kim2022blaze}, Wonderland~\cite{zhang2018wonderland}, Mosaic~\cite{maass2017mosaic}, Garaph~\cite{ma2017garaph}, GraFBoost~\cite{jun2018grafboost}, and many more.
These systems have democratized running graph analytics, allowing users to run computations on their trillion-edged graphs on a single machine at a fraction of the cost of doing the same on a cluster.
