\TLS{New data are being generated rapidly, and there is an ever-present and growing need to store and analyze them efficiently.}
Much of this data has some inherent schema or structure, and relational databases are a natural choice for efficiently storing it.
Relational databases(RDBMS) have been the backbone of data management for six decades and have been extended to service new and emerging use cases, such as analytical databases that allow efficient scans on skippable columns~\cite{stonebraker2018c,boncz2005monetdb}.
RDBMS are perfectly well suited to store structured or semi-structured data that contains attributes and experiences updates and has stringent consistency requirements: such a workload is called Online Transactional Processing (OLTP).
More involved analysis of data involves full dataset scans and extensive join processing, and these "business intelligence (BI) style" workloads are called Online Analytical Processing (OLAP).
Several OLAP databases and data warehousing solutions exist to enable this workload at an enterprise scale~\cite{Redshift2015,boncz2005monetdb,vertica, raasveldt2019duckdb}.

\TLS{Several data are interesting for containing some latent features that are interesting for analysis that would be more efficiently handled in a specialized system.}
Take, for example, a social network: the user profile is usually structured and conforms to some known schema, while the content of any individual "column" of information on a user's profile can be unstructured.
This schema can be easily managed and stored in a relational database, as is done at Meta~\cite{bronson2013tao}.
The social network database contains "follower" and "repost" relationships that form large graphs and are often modeled as adjacency lists.
Graph analysis tasks can require accessing the whole (or a significant part of the) graph.
RDBMSs do not perform well for whole-graph analytics tasks since they need to perform recursive self-joins to answer queries, and graphs usually have far too many rows for this to be an effective strategy~\cite{TransitiveClosureBiskupStiefeling1989}.

\TLS{In the meantime, large graphs have become  ubiquitous~\cite{ubiquityLargeGraphsVLDB2017} and graphs with trillions of edges and billions of nodes are now common~\cite{ProjectGDELT, WDCHyper94:online}.}
Analyzing datasets of this scale requires creating systems that can handle the enormous scale of the data efficiently while remaining economical to own and operate.
Graphs are therefore sufficiently different and interesting that many specialized systems have been proposed to store and process them; popular graph databases include Neo4j~\cite{neo4j}, ArangoDB~\cite{arangodb} and popular graph processing systems include Pregel~\cite{malewicz2010pregel}, GraphX~\cite{gonzalez2014graphx}, PowerLyra~\cite{powerlyra2019}, GraphChi~\cite{kyrola2012graphchi} and Ligra~\cite{shun2013ligra}.

\TLS{Similar to traditional databases, graphs can also have transactional and analytical workloads.}
Transactional (Graph OLTP) workloads are short queries on the graph to get (or set) some localized information, for instance, in a social network, a user might wish to see the latest posts made by their friends, or the changes to the network as a new friend joins the social network.
Such \emph{interactive} queries are latency-sensitive, with many tasks such as fraud detection in financial networks demanding 20 ms latencies~\cite{qiu2018real}.\\
Analytical workloads on graphs (Graph OLAP) are queries about the network that can be answered only through a "whole-graph" analysis.
For instance, a cloud service provider might wish to establish which clients have been exposed to an attack by using the login information log.
One possible way to do this would be to run traversal queries from the affected clients and establish a \emph{blast radius} of possibly infected machines.
This task must interact with large parts of the graph, if not the whole graph, and will typically take longer to finish.
There are specialized systems to handle these workloads: Graph Processing Systems(Section~\autoref{back:scaling_gps}) to handle the whole-graph analytics workloads, and Graph Databases (Section~\autoref{back:graphDB}) to handle the short, interactive queries on the graph data.

\section{State of the Art: What's good?}
\label{intro:whats_good}
In light of the existing architectures in the graph-processing research landscape, we identify a set of requirements for a single-node graph processing system.
\begin{enumerate}
    \item \textbf{Efficient out-of-the-box algorithms and a rich, useful API for expressing computations}: Using efficient algorithms is essential for correctly benchmarking the system and establishing areas that need improvement for future research~\cite{mcsherry2015scalability, beamer2016understanding, mehrotra2024sok}. Additionally, it is very useful to have an intuitive and flexible API that allows the user to write custom algorithms.
    \item \textbf{Using well-designed data structures that can be parallelized without incurring severe penalties from locking overheads} is critical in designing massively parallel graph processing systems that use fast storage devices. 
    % Blaze~\cite{kim2022blaze}, for instance, has been designed to maximize the bandwidth utilization of a fast NVMe SSD by reducing the amount of locking and the use of compare-and-lock style update propagation that is common in other graph processing systems designed to run on flash storage.
    \item \textbf{Using data layouts that maximize sequential access to the graph are preferred} and painstakingly designed. This has been the central theme for much research in semi-external graph processing\footnote{In semi-external systems, vertex and algorithmic state is maintained in RAM and the graph edges are read from the storage device}, and every system has its clever scheme to address this problem for its API and computation model. Creating specialized data layouts requires preprocessing the graph, which is a significant overhead compared to the cost of actually running the computation. Preprocessing costs are rarely amortized.
\end{enumerate}

\subsection{Single-node optimization before scale-out}
\TLS{Past research has conclusively shown that premature distribution of tasks based on poor single-node baselines is bound to underperform.}
McSherry et al.~\cite{mcsherry2015scalability} demonstrated that several popular distributed GPS evaluated their scalability by comparing not against an efficient single-threaded implementation but by evaluating how the run time changes as the total number of threads increases.
This led to several attempts at standardization of benchmarking practices for GPS~\cite{capotua2015graphalytics,mehrotra2024sok,beamer2015gap,graph500}, with each proposal identifying the need to use more performant algorithms and reporting more detailed performance metrics.
Considering that distributed graph processing is inefficient due to the communication costs, the main benefit of using a cluster for graph processing is that the aggregate RAM might be sufficiently large to process a bigger graph than can be done on a single machine.
The Waterloo survey on the state of graph processing reveals that large graphs are ubiquitous, and several of their participants claimed to operate on uncompressed graphs larger than 1 TB; the exact upper limit on the size of these graphs is unknown~\cite[Section~3.2]{ubiquityLargeGraphsVLDB2017}.
While servers with more than a few terabytes of RAM are not uncommon, they are expensive and, as we and others have shown, unnecessary.
Scale-out systems built from semi-external graph processing systems should provide better dollar-to-dollar performance than a distributed graph/data processing system.
We want to design and optimize a single-node, single-socket graph database before developing NUMA capabilities and, eventually, a distributed graph database.

\subsection{Best-of-both worlds design for mixed OLAP and OLTP workloads}
\TLS{We have seen in Section~\autoref{intro:whats_good} that the system performance is strongly linked to the in-memory and on-disk layout and that significant preprocessing effort is spent in creating and maintaining these layouts.}
Time spent to preprocess the graph will rarely get amortized; it varies by the freshness requirements for the workload and the rate at which new snapshots or increments need to be analyzed.

A better alternative is to natively store the graph in a format similar to or close to the in-memory representation required for efficient access.
Graph databases do this but are optimized for transactional point queries rather than full-graph analytics.
Neo4j~\cite{neo4j}, for instance, stores all graph data on disk as "linked lists of fixed size records" \cite{neo4j:data_layout:2024}.
A linked-list representation of graphs is great for connectivity queries but is bound to cause catastrophic random access overhead when running whole graph analytics.
Newer research systems such as GraphFlowDB~\cite{graphflowdb2021Gupta} provide a more methodical analysis of design decisions required to store a property graph in memory. Still, they do not persist or evaluate the system on whole-graph analytics benchmarks.
Storing a graph larger than available RAM requires careful persistent and in-memory data layout co-design, which performs well on both OLAP and OLTP-style workloads.

\subsection{In-Database Analytics}
We have already examined the use of specialized graph processing systems for analytics tasks and know they are typically not transactional and do not support point queries.
Graph databases are transactional and perform well on point queries but are orders of magnitude slower than specialized graph processing systems~\cite{SpecializedGDB-Waterloo} on whole-graph analytics tasks.
Therefore, the state-of-the-art in graph data management has evolved around a split system design: graph database systems for point queries and specialized high throughput graph processing systems for whole-graph analysis tasks.
This leads to freshness mismatch between the data stored in the original data store, what's available for point-query analysis following ingestion into a graph database, and what's available for batch analysis in a specialized graph processing system.
The split system design also causes the creation of data silos which need constant ETL and data movement to maintain consistency.

These problems have an equivalent in the relational database world: the constant data transformation needed to maintain consistency between a row-store and a column store~\cite{HTAP2016ArchepelagoArulraj}, and the subsequent development of Hybrid Transactional and Analytical Processing (HTAP) databases is a promising solution.
Similar solutions must also be developed for analyzing graphs, and recent commercial graph databases, such as GART~\cite{shen2023bridging}, have started offering solutions for real-time graph analytics workloads.
GART stores the extracted graph in memory since it has been designed for latency and freshness-sensitive tasks, such as fraud detection, and not for further downstream batch processing tasks we target.
Graph HTAP systems should be designed to handle efficient real-time analytics and more intensive whole-graph processing tasks.
