\chapter{Introduction}

\TLS{New data are being generated rapidly, and there is an ever-present and growing need to store and analyze them efficiently.}
Much of this data has some inherent schema or structure, and relational databases are a natural choice for efficiently storing it.
Relational databases have been the backbone of data management for six decades and have been extended to service new and emerging use cases, such as analytical databases that allow efficient scans on skippable columns~\cite{stonebraker2018c,boncz2005monetdb}.
Relational databases are perfectly well suited to store structured or semi-structured data that contains attributes and experiences updates and has stringent consistency requirements: such a workload is called Online Transactional Processing (OLTP).
More involved analysis of data involves full dataset scans and extensive join processing, and these "business intelligence (BI) style" workloads are called Online Analytical Processing (OLAP).
Several OLAP relational databases and data warehousing solutions exist to enable this workload at an enterprise scale~\cite{Redshift_2015,boncz2005monetdb,vertica, raasveldt2019duckdb}.

Several data are interesting for containing some dimension for "higher order" analysis that would be more efficiently handled in a specialized system.
Graphs are interesting since they are comprised of both structured (known schema) and unstructured parts (schema-free). 
Take, for example, a social network: the user profile is usually structured and conforms to some known schema, while the content of any individual "column" of information on a user's profile can be unstructured.
These are easily managed and stored in a relational database.
However, the user data in a social network also presents relationships that can be efficiently modeled as a graph and is valuable to be analyzed as such.
Follower relationships and repost relationships in social networks can form large graphs and are often modeled as adjacency lists.
Large adjacency lists also make graph OLTP more challenging since point updates can impact significant parts of the graph and result in long-running "mammoth" write transactions that are either not handled at all or handled poorly~\cite{Cheng2024Mammoths}.
Traditional databases do not perform well for OLAP tasks on large graphs since they need to perform recursive self-joins to answer queries, and graphs usually have far too many rows for this to be an effective strategy~\cite{TransitiveClosure_Biskup_Stiefeling_1989}.

\TLS{There are typically two types of workloads that are commonly run on graphs.}
A user might wish to run short queries on the graph to get some localized information, for instance, in a social network, a user might wish to see the latest posts made by their friends.
This can be expressed as finding the user's immediate friend circle (1-hop neighborhood) and picking their posts.
Such \emph{interactive} queries are latency-sensitive, with many tasks such as fraud detection in financial networks demanding 20 ms latencies~\cite{qiu2018real}.\\
Alternatively, there are some queries about the network that can be answered only through a "whole-graph" analysis.
For instance, a cloud service provider might wish to establish which clients have been exposed to an attack by using the login information log.
One possible way to do this would be to run traversal queries from the affected clients and establish a \emph{blast radius} of possibly infected machines.
This task must interact with large parts of the graph, if not the whole graph, and will typically take longer to finish.
There are specialized systems to handle these workloads: Graph Processing Systems (GPS)(Section~\autoref{back:scaling_gps}) to handle the whole-graph analytics workloads, and Graph Databases (Section~\autoref{back:graphDB}) to handle the short, interactive queries on the graph data.

\TLS{Large data are not new, but graph data management poses unique challenges to system designers, especially when considering evolving graphs.}
Imagine a social network graph where the vertices are people, and the edges are "friends with" relations.
Over time, a popular user (ex., a celebrity or a beloved professor) will aggregate far more friends than the average user.
While there is no significant problem storing such a graph, distributing the graph for fast parallel processing can lead to unbalanced work distribution.
In an evolving graph system, however, storing the graph can be challenging because choosing where to place new vertices can be non-trivial.
For instance, let's say we store Alice's friends near Alice. What do we do when Bob joins the social network, and half of Alice's friends are also Bob's friends?
There is no trivial way to know what's a good layout that satisfies all locality optimization goals.

\TLS{Dynamic graphs need specialized data structures that provide efficient concurrent access and resizing.}
The data structures for storing static graphs do not work well (or at all) on dynamic graphs.
The CSR representation needs expensive reconstruction whenever a graph changes; modified CSRs and their derivatives allow room for growing neighborhoods by leaving space in the CSR ~\cite{PMA_bender2007}, using snapshots to manage updates~\cite{llama}, or by segmenting the CSR such that updates do not force reconstruction of the entire CSR~\cite{csr++_firmli2020}.
Additionally, concurrent reads and writes to the graph can occur in a dynamic environment, and the data structure must provide transactional support to ensure consistency and isolation.
Indeed, designing concurrent data structures for storing dynamic graphs is an important and growing area of research, and many systems have been presented~\cite{graphone_kumar, aspen_feng2021risgraph, stinger_ediger2012, zhu2019livegraph, sortledton_fuchs2022, 10.1145/3639282}.
Databases are ideal for handling large volumes of evolving data since they use persistent data structures that allow automatic resizing and indexing.
Graph Databases, however, perform poorly and are therefore rarely used for whole-graph analytics tasks, being instead relegated to handling dynamic modifications and short interactive queries.

\TLS{This thesis argues that efficient single-node semi-external graph processing should be the foundation for a robust and scalable "best of both worlds" graph data management and analysis system that can handle analytics tasks as well as transactional queries.
Several state-of-the-art design decisions align with this objective, while some need to be modified and revisited.
This thesis presents the design and implementation of a graph database system that stores graphs in analytics-friendly formats and demonstrates that it is possible to build an efficient hybrid system.
There are several design choices in the state-of-art that we build upon and others we modified in service of our objectives.
We now discuss these choices in detail.}

\subsection{Single-node optimization before scale-out}
\TLS{Past research has conclusively shown that premature distribution of tasks based on poor single-node baselines is bound to underperform.} \PM{make single-node great}
McSherry et al.~\cite{mcsherry2015scalability} demonstrated that several popular distributed GPS evaluated their scalability by comparing not against an efficient single-threaded implementation but by evaluating how the run time changes as the total number of threads increases.
This led to several attempts at standardization of benchmarking practices for GPS~\cite{capotua2015graphalytics,mehrotra2024sok,beamer2015gap,graph500}, with each proposal identifying the need to use more performant algorithms and reporting more detailed performance metrics.
Considering that distributed graph processing is inefficient due to the communication costs, the main benefit of using a cluster for graph processing is that the aggregate RAM might be sufficiently large to process a bigger graph than can be done on a single machine.
The Waterloo survey on the state of graph processing reveals that large graphs are ubiquitous, and several of their participants claimed to operate on uncompressed graphs larger than 1 TB; the exact upper limit on the size of these graphs is unknown~\cite[Section~3.2]{ubiquity_large_graphs_vldb2017}.
While servers with more than a few terabytes of RAM are not uncommon, they are expensive and, as we and others have shown, unnecessary.
Scale-out systems built from semi-external graph processing systems should provide better dollar-to-dollar performance than a distributed graph/data processing system.
We want to design and optimize a single-node, single-socket graph database before developing NUMA capabilities and, eventually, a distributed graph database.

\subsection{Best-of-both worlds design for mixed OLAP and OLTP workloads}
\TLS{We have seen in Section~\autoref*{intro:whats_good} that the system performance is strongly linked to the in-memory and on-disk layout and that significant preprocessing effort is spent in creating and maintaining these layouts.}\PM{ This part will talk about native graph storage, hybrid analytics, and transactional design}
Time spent preprocessing the graph is never amortized since each snapshot of an evolving graph is analyzed just once before the ingestion and preprocessing pipelines need to be run again.\MIS{Must that always be true?}
A better alternative is to natively store the graph in a format similar to or close to the in-memory representation required for efficient access.
Graph databases do this but are optimized for transactional point queries rather than full-graph analytics.
Neo4j~\cite{neo4j}, for instance, stores all graph data on disk as "linked lists of fixed size records" \cite{neo4j:data_layout:2024}.
A linked-list representation of graphs is great for connectivity queries but is bound to cause catastrophic random access overhead when running whole graph analytics.
Newer research systems such as GraphFlowDB~\cite{graphflowdb_gupta2021} provide a more methodical analysis of design decisions required to store a property graph in memory. Still, they do not persist or evaluate the system on whole-graph analytics benchmarks.
Storing a graph larger than available RAM requires careful persistent and in-memory data layout co-design, which performs well on both OLAP and OLTP-style workloads.

\subsection{In-Database Analytics} \PM{this is about the freshness of mined graphs and how they must be stored depending on their use case. This is *VERY* similar to the previous subsection, and I don't think I have managed to establish any difference between them.}
Graphs extracted from a primary datastore must be stored in a way conducive to downstream processing, either transactional point queries or whole-graph analytics.
We have already examined the use of specialized graph processing systems for analytics tasks and know they are typically not transactional and do not support point queries.
Graph databases are transactional and perform well on point queries but are orders of magnitude slower than specialized graph processing systems~\cite{specialized_gdb_waterloo} on whole-graph analytics tasks.
Therefore, the state-of-the-art in graph data management has evolved around a split system design: graph database systems for point queries and specialized high throughput graph processing systems (such as the ones we've examined in Section~\autoref{back:scaling_gps}) for whole-graph analysis tasks.
This leads to freshness mismatches between the data stored in the original data store, what's available for point-query analysis following ingestion into a graph database, and what's available for batch analysis in a specialized graph processing system.
The split system design also causes the creation of data silos which need constant ETL and data movement to maintain consistency.

These problems have an equivalent in the relational database world: the constant data transformation needed to maintain consistency between a row-store and a column store~\cite{htap_archepelago_arulraj}, and the subsequent development of Hybrid Transactional and Analytical Processing (HTAP) databases is a promising solution.
Similar solutions must also be developed for analyzing graphs, and recent commercial graph databases, such as GART~\cite{shen2023bridging}, have started offering solutions for real-time graph analytics workloads.
GART stores the extracted graph in memory since it has been designed for latency and freshness-sensitive tasks, such as fraud detection, and not for further downstream batch processing tasks we target.
Graph HTAP systems should be designed to handle efficient real-time analytics and more intensive whole-graph processing tasks.
