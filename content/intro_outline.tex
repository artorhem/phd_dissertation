\TLS{New data are being generated rapidly, and there is an ever-present and growing need to store and analyze them efficiently.}
Much of this data has some inherent schema or structure, and relational databases are a natural choice for efficient storage.
\ac{RDBMS} have been the backbone of data management for six decades and have been repeatedly extended to service new and emerging use cases~\cite{stonebraker2018c,boncz2005monetdb, HStore2008Abadi, stonebraker2013voltdb,PASE2020:pgvector}.
RDBMSs are well-suited for storing and querying structured or semi-structured data on workloads with high volumes of small updates and stringent consistency requirements; these tasks are called \ac{OLTP} workloads.
Larger scale data analysis frequently requires full dataset scans and extensive join processing, and these data warehouse or \ac{BI} workloads are called \ac{OLAP}.
Several relational OLAP databases and data warehousing solutions exist to enable such enterprise scale workloads~\cite{Redshift2015,boncz2005monetdb,vertica, raasveldt2019duckdb}.

% \TLS{Several data are interesting for containing some latent features that are interesting for analysis that would be more efficiently handled in a specialized system.}
However, in some applications, the relationships captured in the data are themselves a fundamentally important object of study. In myriad applications ranging from social network analysis to brain imaging, these relationships form a graph, and that graph itself is important to study and understand.
% For example, in a social network, a user's profile is usually structured and conforms to some known schema, while the content of any individual "column" of information on a user's profile can be unstructured.
% This schema can be easily managed and stored in a relational database, as Meta does~\cite{bronson2013tao}.
For example, a social network maintains information about every user in the network, such as their name, occupation, address, interests, etc.
Meta (Facebook) uses a relational database to store this social network data~\cite{bronson2013tao}.
However, the "network" part of a social network represents important relationships such as ``follows'' or ``likes''.
These relationships form a large graph.
Each vertex of this graph might have associated properties (i.e. schema from the relational table for users), and each edge might also have properties, but almost certainly has a type (or label), that describes the relationship that the edge represents, associated with it.
Graphs in which the nodes have properties and the edges have labels are called Labeled Property Graphs~\cite{besta2020demystifying}.

Graph analysis tasks typically access the whole (or a significant part of the) graph.
If we store the graph only in its relational form, relations (edges) are encoded as joins, and graph traversals turn into recursive self-joins~\cite{10.1145/3129246}.
As a result, \ac{RDBMS}s do not perform well for graph analytics tasks, as computing these recursive self-joins is expensive~\cite{TransitiveClosureBiskupStiefeling1989}.

% \TLS{In the meantime, large graphs have become  ubiquitous~\cite{ubiquityLargeGraphsVLDB2017} and graphs with trillions of edges and billions of nodes are now common~\cite{ProjectGDELT, WDCHyper94:online}.}
In response to this mismatch between graph analysis tasks and relational databases, we have witnessed an explosion in special-purpose systems for storing and processing graph-structured data.
% Analyzing datasets of this scale requires creating systems that can handle the enormous scale of the data efficiently while remaining economical to own and operate.
% Graphs are, therefore, sufficiently different and interesting that many specialized systems have been proposed to store and process them.
Specialized graph databases such as Neo4j~\cite{neo4j} and ArangoDB~\cite{arangodb} follow in the tradition of relational databases, providing a schema-oriented organization and a high-level query language. These systems work well for OLTP workloads but frequently exhibit suboptimal performance on OLAP tasks.
In contrast, a second class of graph processing systems, such as  Pregel~\cite{malewicz2010pregel}, GraphX~\cite{gonzalez2014graphx}, PowerLyra~\cite{powerlyra2019}, GraphChi~\cite{kyrola2012graphchi} and Ligra~\cite{shun2013ligra} are specifically designed to provide outstanding OLAP performance but may not provide OLTP-style query capabilities.

% \TLS{Similar to traditional databases, graphs can also have transactional and analytical workloads.}
% Transactional (Graph OLTP) workloads are short queries on the graph to get (or set) some localized information
OLTP queries on graphs are similar to OLTP queries on more conventional data; for example, in a social network, a user might wish to see the latest posts and replies on their favorite ongoing Twitter feud~\cite{AholeMusk:online}.
Such \emph{interactive} queries are latency-sensitive, with many tasks, such as fraud detection in financial networks, demanding 20 ms latencies~\cite{qiu2018real}.


Analytical workloads on graphs (Graph OLAP) are queries about the network that can be answered only through a "whole-graph" analysis.
% For example, a cloud service provider might wish to establish which clients have been exposed to an attack by using the login information log.
% One possible way to do this would be to run traversal queries from the affected clients and establish a \emph{blast radius} of possibly infected machines.
For example, the recommendation teams at Twitter run PageRank and topic similarity tasks on the user-follow graph to measure the influence of users and recommend new users to follow~\cite{tang2022taming}.
The health teams at Twitter and Facebook run multi-account and fake account detection algorithms on the network graphs to identify and remove fake accounts~\cite{breuer2020friend}.
These tasks must interact with large parts of the graph, if not the whole graph, and will typically take longer to finish.

\section{State of the Art: What's good?}
\label{intro:whats_good}
State-of-the-art systems typically assume that graph databases and graph processing systems run on a distributed collection of nodes.
We, instead, start with the assumption that the best distributed system is built from the best single-node system.
Based on this assumption, we identify a set of requirements for building such a single-node graph \ac{HTAP} system.
\begin{enumerate}
    \item \textbf{Efficient out-of-the-box algorithms and a rich, useful API for expressing computations}: Using efficient algorithms is essential for fairly evaluating the system and establishing areas that need improvement ~\cite{mcsherry2015scalability, beamer2016understanding, mehrotra2024sok}. Additionally, it is useful to provide an intuitive and flexible API that allows users to write custom algorithms.
    \item \textbf{Using well-designed data structures that can be parallelized without incurring severe penalties from locking overheads} is critical in designing parallel graph processing systems that leverage today's multicore compute infrastructure and fast storage devices. 
    % Blaze~\cite{kim2022blaze}, for instance, has been designed to maximize the bandwidth utilization of a fast NVMe SSD by reducing the amount of locking and the use of compare-and-lock style update propagation that is common in other graph processing systems designed to run on flash storage.
    \item \textbf{Using data layouts that maximize sequential access to the graph are preferred} and painstakingly designed. This has been the central theme for much research in semi-external graph processing\footnote{In semi-external systems, vertex, and algorithmic state is maintained in RAM and the graph edges are read from the storage device}, and every system has its own clever scheme to address this problem for its API and computation model. Creating specialized data layouts requires preprocessing the graph, which is a significant overhead relative to the cost of running many computations. Preprocessing costs are rarely amortized.
\end{enumerate}

We build upon these ideas to create \project{}.

\section{State of the Art: What needs to be changed?}
\label{intro:what_change}
% \PM{The basic flow: on-disk layouts that match in-memory layouts, using a database that lets one work on dynamic graphs larger than memory, building an HTAP graph database that does not need to run analytics independently from transactions, making the single-node system perform great before scaling to a cluster/NUMA setting.}
% \\\\
% \TLS{Based on the state of the art in graph data management, there is much that needs to change to accommodate}
Graph data management has a fork in the road: one set of systems focuses on high-throughput whole-graph analytics, while the other focuses on low-latency OLTP-style processing; data is transferred between these systems via extract-transform-load pipelines.
\project{} is designed to find a best-of-both-world solution in this landscape that reduces cross-silo data movement and preprocessing costs. 
We base the ~\project{} design on a few key principles that we lay out in the following subsections, namely, single-node optimization, in-database analytics, and bridging the gap between graph OLAP and graph OLTP systems.

\subsection{Single-node optimization before scale-out}
\TLS{Past research has conclusively shown that premature distribution of tasks based on poor single-node baselines is doomed to perform badly.}
McSherry et al.~\cite{mcsherry2015scalability} demonstrated that several popular distributed GPS evaluated their scalability by comparing, not against an efficient single-threaded implementation, but by showing how the run time changes as a function of the number of threads.
When McSherry compared these scalable systems to an efficient sequential implementation, he revealed that some systems could not match ``laptop performance'' regardless of how many machines were used!
This stunning result led to several attempts at benchmark standardization efforts for GPS~\cite{capotua2015graphalytics,mehrotra2024sok,beamer2015gap,graph500}. Each proposal identified the need to use more performant algorithms and report more comprehensive performance metrics.
Considering that distributed graph processing is fundamentally inefficient due to the communication costs, the main benefit of using a cluster for graph processing is that the aggregate RAM might be sufficiently large to enable processing graphs entirely in memory, even if their size is larger than the memory of a single machine.
The Waterloo survey on the state of graph processing~\cite{ubiquityLargeGraphsVLDB2017} reveals that large graphs are ubiquitous, and several of their respondents reported operating on uncompressed graphs larger than 1 TB; the exact upper limit on the size of these graphs is unknown~\cite[Section~3.2]{ubiquityLargeGraphsVLDB2017}.
While servers with more than a few terabytes of RAM exist, they are expensive and, as we and others have shown, unnecessary.
Scale-out systems built from semi-external graph processing systems should provide better price performance than a distributed graph/data processing system.
We want to design and optimize a single-node, single-socket graph database before requiring distribution.

\subsection{Best-of-both worlds design for mixed OLAP and OLTP workloads}
% \TLS{We have seen in Section~\autoref{intro:whats_good} that the system performance is strongly linked to the in-memory and on-disk layout and that significant preprocessing effort is spent in creating and maintaining these layouts.}
\TLS{As reported in section ~\ref{back:graph_rep}, many graph processing systems require expensive pre-processing steps to construct a suitable on-disk data layout that allows fast sequential access to the graph.}
Time spent preprocessing the graph is rarely amortized; it varies by the freshness requirements for the workload and the rate at which new snapshots or increments need to be analyzed.

A better alternative is to natively store the graph in a format similar to or close to the in-memory representation required for efficient access.
Graph databases do this but are optimized for transactional point queries rather than full-graph analytics.
Neo4j~\cite{neo4j}, for instance, stores all graph data on disk as "linked lists of fixed size records" \cite{neo4j:data_layout:2024}.
A linked-list representation of graphs is great for connectivity queries but is bound to cause catastrophic random access overhead when running whole graph analytics.
Newer research systems such as GraphFlowDB~\cite{graphflowdb2021Gupta} provide a more methodical analysis of design decisions required to store a property graph in memory. Still, they do not persist or evaluate the system on whole-graph analytics benchmarks.
Storing a graph larger than available RAM requires careful persistent and in-memory data layout co-design, which performs well on both OLAP and OLTP-style workloads.

\subsection{In-Database Analytics}
We examined the use of specialized graph processing systems for analytics tasks and know they are typically not transactional and do not support point queries.
Graph databases are transactional and perform well on point queries but are orders of magnitude slower than specialized graph processing systems~\cite{SpecializedGDB-Waterloo} on whole-graph analytics tasks.
Therefore, state-of-the-art graph data management has evolved around a split system design: graph database systems for point queries and specialized high throughput graph processing systems for whole-graph analysis tasks.
This leads to a freshness mismatch between the data stored in the original data store, what's available for point-query analysis following ingestion into a graph database, and what's available for batch analysis in a specialized graph processing system.
The split system design also causes the creation of data silos which need constant \ac{ETL} and data movement to maintain consistency.

These problems have an equivalent in the relational database world: the constant data transformation needed to maintain consistency between a row-store and a column store~\cite{HTAP2016ArchepelagoArulraj}, and the subsequent development of \ac{HTAP} databases is a promising solution.
Similar solutions must also be developed for analyzing graphs, and recent commercial graph databases, such as GART~\cite{shen2023bridging}, have started offering solutions for real-time graph analytics workloads.
GART stores the extracted graph in memory since it has been designed for latency and freshness-sensitive tasks, such as fraud detection, and not for further downstream batch processing tasks we target.
Graph \ac{HTAP} systems should be designed to handle efficient real-time analytics and more intensive whole-graph processing tasks.

\section{What have we done?}
\TLS{This thesis presents the design of a flexible and performant \ac{HGTAP} database system that performs better than custom-created graph processing systems on analytics tasks and is competitive against graph databases on transactional point queries.}

Our system, \project{}, has been designed for a single-node setting and provides a fully transactional API for updating and querying a graph. We provide snapshot-level read-only iterators for fast serial reads for analytical tasks.
\project{} has been designed to eliminate any preprocessing tasks needed before running analytics and provides two layouts we designed to get strong sequential iterator-based read performance common in analytics tasks.
The API is flexible enough to let users write algorithms as vertex or edge programs; we demonstrate our performance by modifying GAP-BS to use our API and demonstrating that our analytics tasks have robust performance compared to other semi-external and in-memory systems when factoring in their pre-processing times.

The contributions of this thesis are:
\begin{enumerate}
    \item The design of a Graph HTAP database takes a "best-of-both-worlds" approach to deliver robust performance on whole-graph analytics tasks and transactional queries without the need for constant preprocessing or ETL.
    % \item I can't think of anything else
    \item We present a principled analysis of analytics friendly data layouts and how we use a mature key-value store (WiredTiger~\cite{WiredTigerDocumentation}) as the storage engine to store and access the graph. The API provided by \project{} allows the user to do fast neighborhood scans by using scan cursors and provides an API for persisting the algorithmic state of graph processing tasks to bootstrap future rounds of computations.
    \item \project{} provides a multi-threaded bulk-insertion tool for quickly loading the initial graph into the database. Most other bulk-insertion tools require a single-writer to the database due to consistency requirements; we relax these requirements for fast bulk insertion.
    \item We provide a comprehensive performance analysis of \project{} against graph databases and graph processing systems (in-memory, semi-external, and dynamic) to show that we are competitive in all cases, but with lower data migration cost due to low/no preprocessing and ETL costs.
    \end{enumerate}

The remainder of this thesis proceeds as follows:
In \autoref{chapter:background}, we provide the background that motivates our work. 
We begin by describing the data structures used to represent graphs efficiently in memory using layouts that maximize sequential access, particularly the most popular layouts: \ac{CSR} format (\autoref{back:CSR}), Adjacency Lists (\autoref{back:adjlist}), and Edge Logs (\autoref{back:persistent_rep:TEL}).
We discuss the design of data layouts in graph processing systems in Section~\autoref{back:scaling_gps} and graph databases in Section~\ref{back:graphDB}.
Following that, we examine how semi-external systems create on-disk layouts that allow efficient access to the graph.
We then turn our focus towards graph databases, and examine the transactional queries for which they are optimized.
With this context in place, we contrast graph databases and graph processing systems, establishing the central dichotomy of graph data management and lay the foundation to discuss our hybrid graph transactional and analytical system design.

\autoref{chapter:architecture} presents the design of \project{}.
We begin by describing our graph API and then introduce the three layouts for which we provide that API.
Next, we describe the iterators we provide for efficiently accessing graph elements: nodes, edges, and neighborhoods of nodes. We conclude with a description of work assignment and thread scheduling for reduced-conflict writes to the graph.
Finally, we discuss the optimizations we provide for maintaining the algorithmic state and using results from previous computations to jumpstart new rounds of computation.\\
