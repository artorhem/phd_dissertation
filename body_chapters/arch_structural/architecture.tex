\chapter{Structural Graph Storage in FlexoGraph}
\label{sec:architecture:structural}

% Chapter preamble: scope and structure
This chapter describes the design and implementation of \project{}'s structural graph storage layer.
A graph database must efficiently store and retrieve both the graph's topology (vertices and edges) and the properties attached to them.
Since analytics tasks operate primarily on the structural graph while point queries and neighborhood queries access properties, these two concerns impose different (sometimes conflicting) layout requirements.
\project{} therefore separates the graph structure from the properties and labels associated with the nodes and edges, devoting a distinct storage layer to each.

The chapter breakdown of this thesis mirrors this architectural decision.
This chapter focuses on how \project{} stores and accesses the structural graph: its design principles, data encoding, two structural representations, the graph API, topology cursors, partitioning for parallel analytics, and bulk loading.
The next chapter (\autoref{sec:architecture:property}) builds on this foundation to describe how \project{} stores properties and labels.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{What Should a Graph Database Provide?}
\label{arch:requirements}

In~\autoref{sec:bg:workloads}, we discussed the different workloads that are commonly applied to graph-structured data and the access patterns they exhibit.
A graph database should provide the following:
\begin{itemize}
\item Storage \textbf{formats} that provide good performance on the common access patterns identified in~\autoref{sec:bg:workloads}.
\item A high-level \textbf{API} that hides the underlying data structures behind a uniform interface, so the user can query her graph without knowing its internal representation.
\item A \textbf{framework} to permit efficient implementation of common operations, such as neighborhood collection and traversal. Efficient iterators on the graph elements are critical for performance and should be first-class primitives in the system.
\end{itemize}

To illustrate how these requirements combine in a real application, consider computing PageRank on a graph.
\autoref{alg:PageRankPullGS} shows the pseudocode for the PageRank algorithm.
\begin{algorithm}
  \begin{algorithmic}[1]
  \Require Graph $G = (V,E)$ where $V$ is the set of nodes and $E$ is the set of edges
  \Require Damping factor $kDamp \in (0, 1)$, typically $kDamp = 0.85$
  \Require Tolerance $\epsilon > 0$, typically $10^{-4}$
  \Ensure PageRank vector Scores
  \State $init\_score = \frac{1.0}{|V|}$
  \State $base\_score = \frac{1.0 - kDamp}{|V|}$
  \State $Scores(v) = init\_score$ for all $v \in V$
  \State $Outgoing\_vals(v) = 0$ for all $v \in V$
  \ForAll{\highlightP{$v \in V$}}
      \State \highlightM{$Outgoing\_vals(v) \gets \frac{init\_score}{|N^+(v)|}$}
  \EndFor
  \For{$i = 1$ to $max\_iters$}
      \State $\Delta = 0$
      \ForAll{\highlightP{$v \in V$}}
          \State $incoming\_total = 0$
          \ForAll{\highlightB{$u \in N^-(v)$}}
              \State $incoming\_total \gets incoming\_total + Outgoing\_vals(u)$
          \EndFor
          \State $old\_score \gets Scores(v)$
          \State \highlightM{$Scores(v) \gets base\_score + kDamp \cdot incoming\_total$}
          \State $\Delta \gets \Delta + (Scores(v) - old\_score)$
          \State \highlightM{$Outgoing\_vals(v) \gets \frac{Scores(v)}{|N^+(v)|}$}
      \EndFor
      \If{$\Delta < \epsilon$}
          \State \textbf{break}
      \EndIf
  \EndFor \\
  \Return $Scores$
  \end{algorithmic}
  \caption{PageRank Algorithm as specified in the GAP Benchmark~\cite{beamer2015gap}: this variant allows new values to be immediately visible (Gauss--Seidel style). The highlighted lines indicate different access patterns: \highlightP{iteration over the vertex set}, \highlightB{access to a vertex's neighborhood}, and access to \highlightM{the results vector}. For a vertex $v$, $N^+(v)$ denotes its out-neighborhood, and $N^-(v)$ its in-neighborhood.}
  \label{alg:PageRankPullGS}
  \end{algorithm}

Implementing PageRank in a graph database exercises all three requirements:
\begin{itemize}
\item \textbf{Formats:} The algorithm must scan the full vertex set (\highlightP{lines 5, 10}) and, for each vertex, iterate over its incoming neighbors (\highlightB{line 12}). The storage format must support both operations efficiently.
\item \textbf{API:} The application must create vertex iterators for efficient scans over the vertex set and neighborhood iterators for scanning a vertex's in-neighborhood, without knowing the underlying storage layout.
\item \textbf{Framework:} As the algorithm processes each vertex, it reads and writes the vertex's score and outgoing value (\highlightM{lines 15, 16, 18}). These per-vertex computations must compose with the iteration primitives to yield an efficient end-to-end implementation.
\end{itemize}

\section{Design Principles}
\label{arch:design-principles}

A graph database must store and retrieve both the structural graph and its properties efficiently, across the full range of workloads discussed in~\autoref{sec:bg:workloads}.
Because analytics tasks operate on the structural graph and point and neighborhood queries access properties, these two concerns demand different storage layouts.
A \textbf{graph database should therefore store the graph structure independently of the properties and labels associated with nodes and edges.}
The structural graph and the property store need different layout optimizations, and separating them widens the optimization space.
For example, the structural graph benefits from compact, cache-friendly encodings optimized for sequential scans and high fan-out traversals; properties benefit from columnar layouts that support selective column reads and schema-per-label storage.

We use the \wt{} key-value store as our persistence layer, because it provides three properties essential for graph analytics:
excellent multi-threaded (non-blocking) read performance, ACID-compliant MVCC reads, and scaling to datasets larger than RAM.

Since \wt{} is an embedded KV store, \project{} runs as a single process: each thread opens a private session with its own cursors, so reads never contend across threads.
Writes use snapshot isolation: when concurrent transactions modify the same key, \wt{} commits one and rolls back the rest.

\project{} addresses the three requirements identified in~\autoref{arch:requirements} as follows.
\emph{Requirement~1} (formats) is met by providing two structural representations, Adjacency List and EdgeKey, each with distinct performance tradeoffs (this chapter).
\emph{Requirement~2} (API) is met by the \code{GraphBase} abstraction, which hides the choice of representation behind a uniform interface for node/edge manipulation, degree queries, and cursor creation.
\emph{Requirement~3} (framework) is met by topology cursors and partitioning strategies that enable efficient parallel traversal and analytics.

\section{Structural Representations}
\label{arch:structural-reps}

\project{} provides two graph representations that mimic the two most common layouts used in in-memory graph processing: Adjacency Lists (\autoref{arch:adjlist}), and EdgeKey (\autoref{arch:edgekey}), which approximates a CSR.

\subsection{Data Encoding}
\label{arch:data-encoding}

\project{} stores vertex IDs as 64-bit unsigned integers in big-endian 8-byte blobs.
Big-endian encoding ensures that \wt{}'s lexicographic key comparison (\texttt{memcmp}) coincides with numeric order.
This avoids the overhead of \wt{}'s native variable-length integer encoding (format codes \texttt{I} and \texttt{Q}), which requires decoding during comparison; with raw big-endian blobs, key comparison is a direct \texttt{memcmp} with no per-byte interpretation.
The compiler intrinsic \texttt{\_\_builtin\_bswap64} performs the byte-swap before handing keys to \wt{}.

\project{} stores degree counts as 32-bit unsigned integers and edge weights as double-precision floats per the Graphalytics specification~\cite{capotua2015graphalytics}.

In~\autoref{arch:typed-ids}, we extend this encoding to embed a label tag in the top 8 bits of the vertex ID, enabling $O(1)$ label extraction without a table lookup.

\subsection{Adjacency List Representation}
\label{arch:adjlist}

The adjacency list representation uses two adjacency tables to store in- and out-neighborhoods separately (\autoref{fig:schema:adjlist}).
Each adjacency table is keyed by a big-endian vertex ID; the value is a packed byte blob containing the vertex's degree followed by its neighbor IDs.
Concretely, the value format is:
\[
  \texttt{[degree}_{32} \;|\; \texttt{nbr\_id}_1 \;|\; \texttt{nbr\_id}_2 \;|\; \cdots \;|\; \texttt{nbr\_id}_{d}\texttt{]}
\]
where $d$ is the degree and each neighbor ID is an 8-byte big-endian blob.
The table uses \texttt{value\_format=u} (raw, untyped bytes), as the \code{WT\_MODIFY} API requires.

This format lets us modify adjacency lists via the \code{WT\_MODIFY} API (\autoref{sec:wt-modify}).
Instead of rewriting the entire value, \code{WT\_MODIFY} stores a change record (an offset, a length, and replacement bytes) in the \wt{} cache and write-ahead log (if enabled).
On an edge insertion, \code{WT\_MODIFY} appends the new neighbor ID to the blob and updates the degree prefix, recording only the delta (the 8-byte neighbor ID and the 4-byte degree update) rather than the full neighbor list.
This reduces cache pressure and WAL volume, particularly for high-degree vertices where the full adjacency list may span tens of kilobytes.

Concurrent insertions to high-degree vertices, however, contend because they modify the same blob: each \code{WT\_MODIFY} targets the same key, and under snapshot isolation only one such modification can commit.
This motivates the EdgeKey representation (\autoref{arch:edgekey}), where each edge is an independent key-value pair.

Edge deletion in the adjacency list is more expensive than insertion.
Deleting an edge requires locating the neighbor ID within the blob (a linear scan over the packed array), removing it, shifting the remaining entries, and updating the degree prefix.
Unlike insertion, deletion cannot use \code{WT\_MODIFY}'s append optimization and requires a full read-modify-write cycle.

This format constrains property storage, as \autoref{arch:prop-embedded} describes.
For undirected graphs, a single adjacency table stores each edge $(a\text{ --- }b)$ as two directed entries: $(a \rightarrow b)$ and $(b \rightarrow a)$.

In read-optimized mode, an additional node table stores each vertex's in-degree and out-degree, avoiding a full adjacency-list scan for degree queries.
For weighted graphs, a separate edge table with composite key $(src, dst)$ stores edge weights.

\subsection{EdgeKey Representation}
\label{arch:edgekey}
The EdgeKey representation stores vertices and edges in a single sorted B-tree, keyed by ($src\_id, dst\_id$).
A reserved out-of-band destination ID (\texttt{0}) marks vertex entries; all other entries are edges.
Since \texttt{0} is reserved for the node sentinel, \project{} transparently shifts every user-provided ID by $+1$ before storage and by $-1$ during retrieval.
This is a single-line operation (\code{MAKE\_EKEY(id) = id + 1}).

The value is interpreted as follows:
\begin{itemize}
  \item For node entries, the value contains the serialized \code{in\_degree} and \code{out\_degree} in read-optimized mode or a 1-byte dummy value in the (default) write-optimized mode.
  \item For edge entries, the value contains the edge weight for weighted graphs or a 1-byte sentinel (\texttt{0x00}) for unweighted graphs.
\end{itemize}
Lexicographic key order guarantees that each node entry precedes its outgoing edges.
To scan the out-neighborhood of \code{src\_id}, we position the cursor at \code{(src\_id, 0)} and iterate over all keys with prefix \code{src\_id}.

\paragraph{Evolution to Split EdgeKey.}
The original EdgeKey design used a single table with an index on \code{(dst\_id, src\_id)} for in-neighborhood access.
This design required either a full table scan or a secondary index lookup to find a vertex's in-neighbors, both unacceptably slow for random in-neighborhood seek-and-scan workloads.
To remedy this, \project{} materializes the in-neighborhood in a separate \code{edge\_in} table, keyed on $(dst\_id, src\_id)$, producing the \emph{Split EdgeKey} representation (\autoref{fig:schema:edgekey}).
The Split EdgeKey trades additional disk space for significantly faster in-neighborhood access, a classic time-space tradeoff.
\project{} maintains the \code{edge\_in} table internally and does not expose it through the API.

\paragraph{Leaf page density.}
The EdgeKey representation encodes topology entirely in keys: a structural traversal iterates over keys without calling \code{get\_value()}.
With 1-byte sentinel values for unweighted edges, a 4\,KB leaf page holds approximately 250 edges (16-byte composite key + 1-byte value each), compared to roughly 50 entries for a row store with full-width values.
This high key density reduces the number of pages touched per neighborhood scan.

\subsection{Comparison}
\label{arch:comparison}
The two representations offer complementary tradeoffs:

\begin{itemize}
  \item \textbf{Read (full neighborhood):} The adjacency list stores each vertex's full neighborhood in a single blob, enabling fast sequential reads in one I/O. EdgeKey requires scanning multiple B-tree entries, touching more pages.

  \item \textbf{Write (edge insert):} EdgeKey is a single independent key-value insert with no contention on existing rows. The adjacency list requires a read-modify-write cycle (mitigated by \code{WT\_MODIFY} delta records but still touching the shared blob).

  \item \textbf{Write (edge delete):} EdgeKey deletes a single key. The adjacency list must scan the blob to locate the neighbor, remove it, and shift remaining entries.

  \item \textbf{Concurrent writes:} EdgeKey inserts to different edges never contend, even for the same vertex, because each edge is a separate key. Adjacency list insertions to the same vertex contend on the shared blob under snapshot isolation.

  \item \textbf{Disk footprint:} The adjacency list is more compact, storing one blob per vertex. EdgeKey stores one row per edge plus key overhead, approximately doubling the on-disk size for undirected graphs.
\end{itemize}

The choice of representation also interacts with the computation model.
Vertex-centric algorithms such as PageRank and BFS iterate over each vertex's neighborhood in turn; they favor the adjacency list's single-blob reads.
Edge-centric algorithms that process edges independently (e.g., streaming edge computations) are a natural fit for EdgeKey's per-edge layout, where each edge is an independent B-tree entry that can be processed without deserializing a vertex's full neighbor list.

We quantify this interaction in~\autoref{sec:eval:ec_vc}, where controlled PageRank and connected-components benchmarks isolate the effect of representation choice under both computation models.

\project{} exposes a C++ library API with two layers: \code{GraphEngine} owns the \wt{} connection, manages checkpoints, and handles partitioning; it creates \code{GraphBase} handles for graph operations.
\code{GraphBase} is an abstract class with virtual methods for node/edge manipulation and property access; \code{AdjList} and \code{SplitEdgeKey} each provide a concrete implementation, so application code is unaware of the underlying storage layout.

The \code{GraphBase} interface has four categories of operations, summarized in~\autoref{tab:graphapi}.
\textbf{Structural operations} manipulate and query the graph topology: adding and deleting nodes and edges, testing existence, querying degrees, and retrieving neighborhoods.
\textbf{Iterator factory methods} return topology cursors for bulk traversal of nodes, edges, and neighborhoods; these are the primary interface for analytics workloads and are discussed in~\autoref{arch:topology-cursors}.
\textbf{Metadata queries} expose graph-level properties such as node and edge counts, the maximum and minimum vertex IDs, and whether the graph is directed or weighted.
\textbf{Management operations} handle checkpointing, closing the database, and cursor cleanup.

\subsection{Topology Cursor Design}
\label{arch:topology-cursors}

\textbf{Topology cursors} provide bulk operations such as scanning all nodes or iterating a neighborhood.
\project{} defines four abstract cursor classes: \code{OutCursor} (out-neighborhood), \code{InCursor} (in-neighborhood), \code{NodeCursor} (node iteration), and \code{EdgeCursor} (edge iteration).
Each representation provides its own cursor implementation: for example, \code{AdjOutCursor} deserializes the packed neighbor blob from a single adjacency table entry, while \code{SplitEKeyOutCursor} iterates successive keys in the edge B-tree.

Cursors wrap \wt{} cursors and manage key-range bounds internally.
The application sets a key range (typically a partition range) via \code{set\_key\_range()}, and the cursor enforces the bounds: each call to \code{next()} returns the next element within the range or signals end-of-range.
This design frees the application from repeatedly checking whether the cursor has left its assigned partition.

The two representations implement \code{next()} differently.
An \code{AdjOutCursor} positions the \wt{} cursor at the adjacency table entry for the current vertex and deserializes neighbor IDs from the packed blob one at a time, advancing to the next vertex when the blob is exhausted.
A \code{SplitEKeyOutCursor} advances the \wt{} cursor to the next key in the B-tree: each key is one edge, so \code{next()} is a single \wt{} cursor advance.

Each thread creates its cursors from \code{GraphBase}, scoped to a partition range that the partitioning strategy described below assigns.

\subsection{Partitioning for Parallel Analytics}
\label{arch:api:partitioning}

Analytics algorithms parallelize over the vertex set: each thread processes a disjoint subset of vertices and their neighborhoods.
Partitioning divides the vertex ID space into non-overlapping ranges so that threads can work independently without synchronization on the structural data.
To run multi-threaded analytics, \texttt{GraphEngine} pins a read-only checkpoint and divides the vertex set into disjoint key ranges.
Each thread receives its assigned range and creates its own topology and property cursors scoped to that range.

\project{} provides three partitioning strategies, each with different cost and load-balance characteristics:
\begin{itemize}
  \item \code{NODE\_COUNT}: Divides the vertex set into equal-sized partitions by node count. Computing the partition boundaries costs $O(1)$ (evenly spaced ID ranges), but degree skew causes load imbalance: a partition containing a few high-degree vertices does far more work than one with only low-degree vertices.

  \item \code{EDGE\_AWARE} (default): Partitions by accumulated out-degree so that each partition contains roughly the same number of edges, balancing work for degree-skewed graphs. Computing the partition boundaries requires a scan of degree counts ($O(|V|)$) to compute prefix sums, but the resulting partitions distribute edge-processing work evenly.

  \item \code{NODE\_COUNT\_FINE}: A finer-grained variant that creates \texttt{num\_threads} $\times$ \texttt{partition\_scale} partitions.  Computing the partition boundaries costs the same $O(1)$ as \code{NODE\_COUNT}, but the finer granularity enables work-stealing schedulers to rebalance load dynamically.
\end{itemize}

For even finer granularity, \code{get\_work\_chunks(chunk\_size)} returns a vector of small, fixed-size key ranges suitable for task-queue-based parallelism (e.g., Cilk, TBB).

The choice of strategy depends on the algorithm.
BFS uses \code{get\_work\_chunks}, because direction-optimizing traversal produces irregular, data-dependent load that benefits from dynamic task-queue scheduling.
PageRank and WCC use \code{EDGE\_AWARE}, because their per-vertex work is proportional to edge count and is uniform across iterations, making static edge-balanced partitioning effective.

Vertex-centric processing on the adjacency list benefits dramatically from \code{EDGE\_AWARE} partitioning (80\,s~$\to$~29\,s, a 2.7$\times$ speedup).
Under \code{NODE\_COUNT}, each thread receives the same number of vertex IDs, but twitter-2010's power-law degree distribution concentrates most edges in a few partitions: the thread assigned to the highest-degree vertices processes orders of magnitude more edges than its peers, and all other threads idle at the iteration barrier.
\code{EDGE\_AWARE} eliminates this straggler effect by balancing edge counts across partitions.

Edge-centric configurations show modest or no improvement because edge partitioning (\code{get\_edge\_range}) already distributes edges evenly by construction; the partitioning strategy governs vertex ranges and affects edge-centric processing only indirectly, through the merge phase.

On soc-LiveJournal (4.84\,M vertices, 68.99\,M edges), \code{EDGE\_AWARE} slightly hurts performance across all configurations: the graph's more uniform degree distribution makes the $O(|V|)$ partition-computation cost outweigh any load-balancing benefit.
This confirms that \code{EDGE\_AWARE} is most valuable on graphs with high degree skew, where load imbalance is most severe.

\section{Edge-Centric vs.\ Vertex-Centric Read-Path Cost}
\label{sec:eval:ec_vc}

In~\autoref{design:rep_comp_pairing}, we argued that each structural representation naturally pairs with a computation model: vertex-centric processing consumes the adjacency list's packed blobs efficiently, while edge-centric processing streams EdgeKey's per-edge entries without reconstruction overhead.
This section validates that claim with two algorithms (PageRank and connected components (WCC)) that isolate the interaction between representation and computation model on the read path.

We run each algorithm in all four combinations of \{vertex-centric, edge-centric\} $\times$ \{adjacency list, EdgeKey\} on two directed graphs: soc-LiveJournal~\cite{socLiveJournal} (4.84\,M vertices, 68.99\,M edges) and twitter-2010~\cite{twitter2010} (41.65\,M vertices, 1.47\,B edges).
All runs use 28 threads with \code{NODE\_COUNT} partitioning.

\paragraph{PageRank.}
The vertex-centric implementation uses the \emph{pull} model: for each vertex~$v$, an \code{InCursor} iterates over~$v$'s in-neighbors, reads source scores, and writes the destination result.\footnote{Vertex-centric and edge-centric PageRank implementations are listed in \autoref{appendix:pagerank_graphapi} and \autoref{appendix:pagerank_ec}, respectively.}
The edge-centric implementation uses the \emph{push} model: each thread streams edges via an \code{EdgeCursor}, accumulates contributions into a private array, and a merge phase reduces the thread-local arrays after each iteration.
Both run 10 iterations.

\paragraph{Connected Components.}
The vertex-centric implementation uses the Shiloach--Vishkin algorithm~\cite{shiloach1982logn}: each thread iterates its partition via \code{OutCursor}, and for each edge, hooks the higher-label endpoint to the lower one, followed by a path-compression pass.
The edge-centric implementation uses label propagation with atomic \texttt{write\_min}: each thread streams edges via \code{EdgeCursor} and propagates the minimum component label along each edge, followed by path compression.
Both iterate until convergence.
We report the wall-clock times for both algorithms on both datasets in \autoref{tab:ec_vc_time}.
We use \wt{} statistics to report the underlying \wt{} B-tree cursor counts for PageRank reported in \autoref{tab:ec_vc_cursors}.

\subsection{Analysis}

\paragraph{Adjacency list: cursor cost amortized across neighbors.}
On the adjacency list, a single \texttt{cursor->next()} call advances to the next vertex's packed blob, and the algorithm reads all~$d$ neighbors via array indexing within the deserialized buffer.
A full graph scan therefore requires $O(|V|)$ cursor calls regardless of the number of edges.
Both computation models confirm this: on soc-LiveJournal, vertex-centric and edge-centric PageRank perform 52.6\,M and 55.8\,M cursor~next calls respectively, consistent with $4.84\text{M} \times 10\text{ iterations}$.
On twitter-2010, the counts are 574\,M and 570\,M; again proportional to~$|V|$, not~$|E|$.

The vertex-centric implementation is faster despite nearly identical cursor counts (1.2\,s vs.\ 3.2\,s on soc-LiveJournal; 78.1\,s vs.\ 138.3\,s on twitter-2010), because it consumes each packed adjacency list directly: the inner loop indexes into the deserialized neighbor array with no per-edge function-call overhead.
The edge-centric implementation pays two additional costs: (1)~the \code{AdjEdgeCursor} yields edges one at a time via \texttt{edgelist[pos{+}{+}]}, adding a virtual call per edge, and (2)~the push model requires a merge phase that reduces 28 thread-local accumulator arrays after each iteration.
Neither cost involves additional cursor operations; the gap is pure compute overhead, not I/O.
The overhead ratio narrows from 2.7$\times$ on soc-LiveJournal to 1.8$\times$ on twitter-2010 because the higher edge density ($|E|/|V| \approx 35$ vs.\ 14) makes the fixed per-vertex merge cost a smaller fraction of total work.
Connected components extends this pattern: on twitter-2010, edge-centric on the adjacency list (16.3\,s) matches vertex-centric (17.0\,s) despite running two additional iterations, because the lower per-edge compute (a comparison and conditional CAS vs.\ floating-point accumulation) narrows the gap to near zero.

\paragraph{EdgeKey: cursor cost paid per edge.}
On EdgeKey, each edge is an independent B-tree entry, so a full scan requires $O(|V| + |E|)$ cursor~next calls, one per node sentinel and one per edge.
The edge-centric configuration confirms this: 795.7\,M calls on soc-LiveJournal ($\approx 73.8\text{M entries} \times 10$) and 21.8\,B on twitter-2010 ($\approx 1.51\text{B entries} \times 10$), plus thread-positioning overhead in both cases.

Vertex-centric processing on EdgeKey is dramatically more expensive: 4{,}943\,M cursor~next calls on soc-LiveJournal (6.2$\times$ the edge-centric count) and 72{,}882\,M on twitter-2010 (3.3$\times$).
The overhead arises, because vertex-centric processing must reconstruct adjacency lists from individual edge entries.
For each vertex, the \code{InCursor} collects edge entries from the B-tree into a vector via repeated \texttt{push\_back} calls, and the algorithm then re-iterates this vector, effectively reading every edge twice.
This reconstruction cost, compounded over 10 iterations and 28 threads, inflates the total cursor operations far beyond the single sequential scan that edge-centric processing requires.
Connected components confirms the pattern: on twitter-2010, edge-centric on EdgeKey is 2.1$\times$ faster than vertex-centric (142\,s vs.\ 301\,s).
The speedup is smaller than PageRank's 4$\times$ because connected components performs less compute per edge, making cursor overhead a larger fraction of total work.

\paragraph{The read-path cost of mutation-friendly storage.}
The natural pairings (vertex-centric on adjacency list, edge-centric on EdgeKey) represent the best each representation can offer.
Across both algorithms, the gap between these pairings ranges from 8$\times$ to 12$\times$.
This is the \emph{read-path cost} of choosing EdgeKey for its mutation advantages: single-entry B-tree inserts with no read-modify-write, no blob contention under concurrent mutation, and $O(1)$ edge deletion.

Edge-centric processing minimizes this cost by working \emph{with} EdgeKey's grain rather than against it.
Vertex-centric on EdgeKey demonstrates what happens when the computation model fights the representation: the system pays the full $O(|V| + |E|)$ cursor cost of EdgeKey \emph{and} the overhead of reconstructing packed adjacency lists that the representation avoids storing by design.
Choosing the right computation model transforms EdgeKey from pathologically slow to a practical, if more expensive, alternative to the adjacency list.

\subsection{Takeaway}

\begin{enumerate}
  \item \textbf{Vertex-centric on adjacency list is consistently the fastest configuration}, because the adjacency list amortizes B-tree cursor calls across all neighbors in a single packed blob.

  \item \textbf{Edge-centric processing recovers most of EdgeKey's read-path cost} by streaming per-edge B-tree entries sequentially, avoiding the reconstruction overhead that vertex-centric processing incurs.

  \item \textbf{The gap between the natural pairings (VC--adjacency list vs.\ EC--EdgeKey) is the irreducible read-path cost of mutation-friendly storage,} and it can be budgeted at design time based on the expected read--write ratio of the workload.
\end{enumerate}
