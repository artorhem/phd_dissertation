\section{Isolating the Persistence Machinery Tax}
\label{sec:wt-ingest-overhead}
\newflag[new: Results from profiling the per-edge overhead when running an ingest-only workload]

\project{} uses \wt{} as its storage engine, because \wt{} provides crash recovery, transactions, and a mature concurrency model.
% EDITED: the configuration is now introduced by the ablation that precedes

% When a workload does not need persistence, \project{} disables write-ahead logging (\texttt{log=(enabled=false)}), checkpoints (\texttt{checkpoint=(wait=0, log\_size=0)}), and raises all eviction thresholds to 100\% so that no eviction work occurs.
\autoref{sec:eval:dynamic:durability} measured the cost of the two mechanisms \project{} disables when a workload does not need persistence, write-ahead logging (\texttt{log=(enabled=false)}) and checkpoints (\texttt{checkpoint=(wait=0, log\_size=0)}).
The profile below adds no further configuration: it keeps \project{}'s eviction thresholds at $80$\% and $95$\% of an $800$\,GiB cache, and at $85$\% and $95$\% for dirty data (\autoref{tab:wt-eviction-knobs}), levels this workload never approaches.
These settings leave almost no disk I/O on the write path; ingesting graph500-24 writes $0.6$\,GiB.

\emph{What CPU overhead does \wt{} still impose on the ingest path once we turn persistence off?}
Answering this question establishes the performance penalty \project{} pays for using a general-purpose transactional storage engine rather than a purpose-built in-memory index.

\paragraph{Persistence components are negligible.}
\label{sec:wt-overhead-persistence}
We use \texttt{perf} to profile the same ingest-only experiment we report in \autoref{sec:dynamic:ingest-update-tput}: graph500-24 ingestion at 1 and 72 writers. 
We then use DWARF\cite{dwarf5standard} to resolve each sample to its \wt{} source function.
Profiling this experiment shows that \project{} spends 13.8\,$\mu$s of writer CPU time per inserted edge at 1 writer, 3.8$\times$ that of Teseo on the same workload.
With WAL and checkpoints disabled, the persistence components (reconciliation, block management, logging, and page splits) account for 46\,ns per inserted edge, under 0.5\% of writer CPU time.
This is a different measurement from the ablation, not a restatement of it.
\autoref{sec:eval:dynamic:durability} prices turning durability \emph{on} ($1.67\times$ on ingest throughput); the 46\,ns here is what persistence code costs while durability is \emph{off}.
Neither quantity accounts for the gap.

\subsection{Where the Time Goes}
\label{sec:wt-overhead-costs}

The costs that dominate the ingest path are intrinsic to \wt{}'s B-tree access path and the bookkeeping that accompanies every page access.

\paragraph{Tree operations.}
B-tree descent and in-memory skip-list insertion account for 39\% of single-writer CPU time, and byte-string key comparison during descent adds another 16\%.
Tree operations are therefore the largest single cost, at 55\%.
Any storage engine that maintains a sorted B-tree over variable-length keys will pay a comparable cost for descent and comparison; this is not specific to \wt{}'s persistence design.
Key \emph{serialization}, the packing step that produces the byte-comparable encoding, accounts for only 1.3\%.
The format conversion itself is cheap; searching with the result is not.

\paragraph{Cache accounting and eviction protocol.}
This row is architecturally distinct from the other costs.
\wt{} manages a \emph{bounded cache}: data lives on disk, and it can evict pages from memory and read them back later.
The entire eviction protocol exists to support this design.
Every piece of per-access bookkeeping in this row traces back to it.
Cache byte counters track memory usage so eviction knows when to trigger, and threshold checks compare those counters against eviction targets on every page access.
Hazard pointers protect pages from being evicted while a thread is reading them.
Each page access also stamps the page with the current value of a connection-wide read generation counter.
Ranking pages by that stamp costs the writers nothing: the eviction server walks the queue and sorts it, and here it evicts nothing (\autoref{tab:wt-eviction-counters}).

A pure in-memory index eliminates all this bookkeeping.
Teseo, for example, has no page cache, no eviction, and no hazard pointers, and pays
nothing in this category.
Yet this protocol runs on every \wt{} page access even when the cache stays far below
every eviction threshold.

At 1 writer, the protocol costs 1,047\,ns per edge (8\%).
At 72 writers, it grows to 18,879\,ns (41\%), an 18$\times$ increase, because every insert
both writes and reads the same connection-wide cache byte counters.
One function, \texttt{\_\_wt\_cache\_page\_inmem\_incr}, accounts for 7,104 of those nanoseconds, against 59\,ns at 1 writer.
Every insert adds atomically to as many as 7 counters that all threads share, and the EdgeKey representation stores almost the whole graph in one B-tree, so even its per-tree counters are shared.

\wt{} creates the eviction server thread unconditionally at connection startup; no configuration can disable it.
It runs a wake-check-sleep loop with an auto-scaling interval, finds nothing to do, and sleeps again; background threads add no measurable time to this row.
The cost measured above comes from the per-access protocol that application threads execute, not the background thread.

None of that cost is eviction work.
\autoref{tab:wt-eviction-counters} gives \wt{}'s eviction counters for this workload, measured in separate runs with statistics enabled.
Ingesting graph500-24 fills $61$\,GiB of the $800$\,GiB cache, well below the $340$ and $380$\,GiB at which eviction would begin (\autoref{tab:wt-eviction-knobs}).
At either thread count, neither the eviction server, nor its workers, nor any application thread evicts a page, and no writer ever waits for cache.
\wt{} force-evicts only the pages that outgrow \texttt{memory\_page\_max}, a path the cache thresholds do not govern.
That accounts for $130$ pages at $1$ writer and $170$ at $72$ writers, all of them within the first $90$\,s, while the tree is still growing.
Eviction work per edge holds steady across the two thread counts while the protocol costs $18\times$ more, so contention on the shared counters, not eviction, explains the growth.

\paragraph{API and transaction bookkeeping.}
Cursor setup and teardown, transaction management (snapshot walks over active sessions, transaction-ID allocation), and \wt{}'s configuration-string parser together account for 13\% at 1 writer.
Under contention these grow sharply: the cursor API alone reaches 6,346\,ns at 72 writers (23$\times$ its single-writer cost), and transaction bookkeeping grows to 5,169\,ns (13$\times$).

\paragraph{Memory allocation.}
At 1 writer, memory allocation and kernel page-fault handling account for 11\% of CPU time.
Much of the page-fault cost is kernel work rather than \wt{} code.
At 72 writers this row drops to 653\,ns, because the faults amortize over a shorter per-edge wall-clock time.

\subsection{Implications}
\label{sec:wt-overhead-implications}

The ingest-path overhead that \project{} pays for using \wt{} with persistence disabled
falls into three categories, summarized in \autoref{tab:wt-overhead-categories}.

\begin{table}[h]
  \centering
  \begin{tabularx}{\columnwidth}{@{}XrrX@{}}
    \toprule
    Category & $w=1$ & $w=72$ & Why it exists \\
    \midrule
    Persistence operations (reconciliation, block mgmt, WAL, page splits)
      & $<$1\% & $<$1\% & Persisting data to disk. Disabled and negligible. \\
    \addlinespace
    Persistence architecture (cache accounting, eviction protocol, hazard pointers)
      & 8\% & 41\% & Bounded-cache design. Runs on every page access even though the cache
        stays $7.6\%$ full and nothing is evicted. \\
    \addlinespace
    B-tree access path (descent, key comparison, transactions, cursor API, key packing)
      & $\sim$69\% & $\sim$49\% & Operating a transactional sorted index. Any storage
        engine with a B-tree, MVCC, and a cursor API will pay a comparable cost. \\
    \bottomrule
  \end{tabularx}

  Percentages are shares of single-writer ($w=1$) and 72-writer ($w=72$) on-CPU time, computed

  \label{tab:wt-overhead-categories}

Persistence \emph{operations} are negligible once we turn WAL and checkpoints off.
The B-tree access path is a cost any transactional sorted index imposes.
The middle category is the one specific to \wt{}'s persistence \emph{architecture}: the
bounded-cache design requires per-access bookkeeping (cache byte counters, threshold
checks, hazard pointers, read-generation stamping) that a pure in-memory index does not need.
At 1 writer, this tax is modest (8\%).
Under contention it grows to 41\%, because all threads contend on the same connection-wide
counters.
It then becomes the largest single component of per-edge cost, ahead of B-tree descent and
of the cursor and transaction layer.

\project{} accepts this overhead, because it can re-enable \wt{}'s crash-recovery
guarantees without changing the data representation.
The bounded cache and its eviction protocol are the mechanism that makes this possible:
they keep the in-memory data organized in pages that \wt{} can reconcile and write to
disk on demand.
